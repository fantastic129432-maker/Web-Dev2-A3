### `adminside/src/app/app.routes.ts`

#### const `routes`

The five pages of the admin website, plus the catch-all.
Every route is lazy, the literal 'events/new' is declared before the
parameterised edit route, and no route sets a static title.
- `@file Routing for the ADMIN-SIDE website.`
WHY EVERY ROUTE IS LAZY
`loadComponent` splits each page into its own chunk, so the dashboard does not
download the event form, and a staff member who only ever reads the
registration list never pays for the editor. The first paint of the admin site
is therefore small even though the application as a whole is not.
ROUTE ORDER MATTERS FOR ONE PAIR
'events/new' must be declared before 'events/:id/edit' is considered - they
cannot actually collide (one has two segments, the other three), but keeping
the literal before the parameterised route is the habit that stops a future
'events/:id' from swallowing 'events/new'.
The page title is NOT set here. Each page sets it through usePageTitle(), which
reacts to the language switcher; a static route `title` would stay English after
the staff member changed language.

### `adminside/src/app/app.ts`

#### class `App`

The application shell: the header and the menu, the content area the router fills,
and the footer.
WHY THE SHELL OWNS THE LAYOUT
The archived admin site had every page call initAdminLayout() to build the same
header and menu, and the brief requires that menu "on all pages". Here the shell
renders it once, so a page physically cannot be missing it - and the pages
themselves contain only their own content. Assessment 2 feedback asked for the
pages to be split into Header, Nav, Body and Footer with the common parts created
once, which is what the four comments in app.html mark.
The <body> class is set here rather than in index.html for a reason: Angular
renders INSIDE <body>, so index.html cannot put a class on an element it does
not own. Two rules in the admin stylesheet are written against
`body.admin-body` (the page background and the admin page heading), so the class
has to exist before the first page paints - which a constructor-time write does.

### `adminside/src/app/core/event-form.ts`

#### function `createTicketTier`

One ticket-tier row, optionally pre-filled from an event being edited.

- `@returns The new row's form group, validated as a whole by `ticketTierValidator`.`

- `@param initial - The event being updated, or null/undefined for a new one.`
- `@returns The empty or pre-filled form group, with the cross-field window rule`

#### type `EventFormGroup`

The form as a whole, so a function's signature can name it.

#### type `EventFormValue`

The form's value. Typed from the form rather than written out by hand, so it

#### function `resetEventForm`

Put the form back to the values it was built with.
ONE CALLER SINCE THE "Clear the form" BUTTON WAS REMOVED (review item 7):
EventForm.reset(), which the edit page calls after a successful save so the form

The tier rows are replaced rather than reset, because they are controls and not

- `@param form - The form group to reset in place.`
- `@param initial - The event to reset to, or null/undefined to reset to a blank`

#### function `isRowInUse`

Is this tier row actually being used?
A row the administrator has not touched at all is not a tier: `ticketTierInputs`
drops it and `ticketTierValidator` ignores it. The free-event lock needs the same
test, because writing a price of 0 into an untouched row would turn it into a
half-filled one - a price with no name - which the API refuses with a 400 naming
a tier the administrator never created.
- `@param row - One row's value.`
- `@returns `true` when any field of the row holds something.`

#### function `toEventInput`

Read the complete body of POST /api/events (or of a full PUT) out of the form.
The two "empty is meaningful" cases are handled explicitly: an empty goal box
is sent as 0 ("no target") and an empty capacity box as null ("no limit").
Omitting them would make the API apply its own default and quietly disagree
with what the administrator sees on screen.
THE DATES
The API requires `eventDate` and derives a missing `dateStart`/`dateEnd` from
it (validateEventBody: `values.dateStart = dateStart || eventDate`). The form
asks for the event's first and last day only, so `eventDate` is DERIVED from
`dateStart` here and the window is sent alongside it:
single-day (the box is ticked)  eventDate = dateStart, and the window is
omitted, which is exactly the shape the API
documents for a one-day event;
multi-day  (the box is clear)   eventDate = dateStart, dateStart and dateEnd
both sent, so the stored window cannot drift
from the payload that produced it.
- `@param form - The complete form group to read.`
- `@returns The request body for POST /api/events or a full PUT, with an empty`
goal sent as 0, an empty capacity sent as null, the event date derived from
the start date and the end date omitted for a single-day event.

#### function `changedFields`

Keep only the fields that actually changed.
PUT /api/events/:id is a PARTIAL update and answers 400 to an empty body, and
sending every field would overwrite a concurrent edit to a column this person
never touched. Both are reasons to send the difference rather than the form.
THE DATES ARE COMPARED AS THE TWO DAYS THE ADMINISTRATOR SEES
`eventDate` is derived from `dateStart` (see toEventInput), and the API derives
date_start and date_end from event_date when the window is omitted - as it is
for a single-day event. So the date fields are removed from the loop below and
decided as one pair, from `storedDates` against `originalDates`. Comparing the
raw fields instead broke in both directions: a stored event whose event_date is
not its first day looked as if the date had changed, and a PUT carrying only
that date made the API collapse a three-day window into one; and ticking
"single-day event" on a stored three-day event looked like no change at all,
so the window could never be collapsed deliberately.
Ticket tiers are included only when the event has none yet: the API adds tiers
to an event that has no tiers and ignores them otherwise (the update form says
so in words), so claiming a tier change was saved would be a lie.
- `@param next - The full payload built from the form.`
- `@param original - The event as the API returned it, or null when there is no`
stored event to compare against.
- `@returns Only the fields that differ, ready to PUT; an empty object when`
nothing changed.

#### const `FIELD_LABEL_KEYS`

The translation key naming each field.
Used in two places: the generic validation messages ("{field} is required")
and the API's per-field 400 details, which name the column rather than the
label. One map means the two cannot disagree about what a field is called.
`eventDate` stays in the map even though the form no longer paints that control:
the API names the column `eventDate` in its own 400 details and names the hidden
control too, so both lookups still need a label.

#### const `REQUIRED_MESSAGE_KEYS`

The message for a required field, when the dictionary has a sentence that
says more than "{field} is required" ("Choose a category.", "Say what the
money funds."). Those keys already existed for the archived admin site, and
using them keeps the wording staff are used to.
`dateStart` is the field that carries the required marker now, so its message
names the event date in words ("The event date is required.") rather than
saying "Start date is required", which would describe a box the form no longer
asks for on its own.

### `adminside/src/app/core/page-title.ts`

#### function `usePageTitle`

Set the browser tab title for an admin route, in the active language.
WHY AN EFFECT AND NOT THE ROUTER'S OWN `title` PROPERTY
A route can carry a static `title`, and that is the simplest thing that
works - in one language. This application has a language switcher, so a
title set once at navigation would stay English after the staff member
switched to Chinese, while every other string on the page changed. Reading
`i18n.t` inside an effect subscribes the title to the language signal, so
both the heading and the tab title move together.
Must be called from an injection context (a component's constructor or a field

is better than a title that silently never updates.

'events.heading'.

### `adminside/src/app/layout/admin-nav/admin-nav.ts`

#### class `AdminNav`

The admin menu, and the NAV segment of the four every admin page shares (Header,
Nav, Body, Footer).
THE MENU IS THE BRIEF'S REQUIREMENT
"Implement a clear and functional menu that allows users to navigate seamlessly
to the other required pages. This menu must be present on all pages." The
archived admin site satisfied it by having every page call initAdminLayout(),
which built the same menu from one array. In Angular that becomes one component
rendered by the application shell, so a new page CANNOT forget the menu - it is
not part of any page's template. Assessment 2 feedback asked for the pages to be
split into Header, Nav, Body and Footer with the common parts built once, which
is why the markup is a file of its own rather than a block inside
admin-header.html.
WHAT THE MENU CONTAINS
Dashboard, Events, Add event, Registrations - the four pages this application
has. The link back to the public website is NOT here: it belongs with the
header's other controls, because it leaves this application entirely and uses
the OTHER_SITE_URL injection token rather than a route.
WHY THE HOST ELEMENT MUST NOT ADD A BOX
The menu is a direct child of the shell's layout: `.admin-nav` is the sticky band
in `adminside/src/styles.css`. `admin-nav.css` gives this host `display: contents`
so the <nav> is laid out exactly where it was before the markup moved, no CSS rule
had to move with it, and - the part that was wrong until this round - the sticky
band has the SHELL's content box to travel in. It used to be confined to
`admin-header`'s own box, whose bottom edge is the menu's own bottom edge, so the
menu scrolled away with the header and `top: 0` never pinned anything; the
measurements and the one-line repair are recorded in `admin-header.css`.
IT PUBLISHES ITS OWN HEIGHT, for the same reason the public site's header does.
`.admin-nav` is pinned at `top: 0`, so it is the band a sticky element below it
has to clear. The event form's right column follows the scroll with
`top: calc(var(--site-header-height) + var(--sticky-card-gap))` (see section 1e
of shared/event-form/event-form.css), and `--site-header-height` is this
element's measured height - a ResizeObserver writing the property onto the
document element, which is exactly what `SiteHeaderComponent` does for the
public header (clientside/src/app/layout/site-header.ts). A ResizeObserver and
not a window `resize` listener, because the value has to follow any reflow of
the menu row - the breakpoints at 760 and 600px above all of them - and a
window resize event does not fire for a reflow that is not the window's.
THE MENU USED TO CHANGE HEIGHT WITH THE LANGUAGE, which is why this is measured
rather than written into the stylesheet. Measured in headless Edge before the
fix: at 390px the menu was 64.39px in English and Chinese against 115.78px in
Vietnamese and Japanese, whose labels wrapped the list onto a second row - a
51.39px error waiting in any written number. The labels now hold one line
(`white-space: nowrap` on `.admin-nav__link`) and the list becomes a two-column
grid at 600px and below (`adminside/src/styles.css`), so the menu has three
heights and THEY ARE THE SAME THREE IN EVERY LANGUAGE: 70.73px above 900px,
64.39px from 601 to 900px - the admin's own 900px block narrows the links'
padding there, not their labels - and 115.78px at 600px and below, where the
grid is. The published value no longer depends on which language the staff
member is reading. The stylesheet's fallback (base.css, section 1) is the
70.73px one, used only for the frame before the first measurement.
No API endpoint is called by this component.

### `adminside/src/app/pages/dashboard/dashboard.ts`

#### class `Dashboard`

The landing page: the state of the event programme at a glance, the events that
need a decision, the API's health, and the five most recent registrations.
ENDPOINTS
GET /api/stats           the headline counts (upcoming events, categories,
organisations, total raised, registrations, tickets
sold). Used INSTEAD of the archived page's habit of
counting the event list in the browser: the API
already computes these, and counting rows client-side
only works while the list fits in one page.
GET /api/admin/events    every event whatever its publishing status, which is
what the needs-attention list is derived from: the
response already carries the publishing status, the
capacity, the registration and ticket counts and the
dates, so no new endpoint was needed for it.
GET /api/health          which data source is answering (DATA_SOURCE=local or

tables it has, and whether the Assessment 3
registrations table exists.
GET /api/registrations   the five most recent registrations.
DELETE /api/registrations/:id   the row's Cancel action.
WHY THE PAGE LOOKS LIKE THIS
The quick-action block ("What do you want to do?") is gone. Its three cards
pointed at /events/new, /events and /registrations - the same three
destinations as the admin menu less than 200px above them - so it was
navigation repeated as content while occupying the prime position under the
statistics. The space it used now carries what the statistics cannot say:
which events have a problem.
The health report is business information only to whoever is debugging, so it
became a compact card in a two-column row instead of a full-width table whose
values stopped around 45% and left half the card empty. It keeps a status
line, three facts, and the complete report one disclosure away, so nothing
that was on the page before has been lost - only re-prioritised.

the brief describes them - what is coming up, then what it has produced.

blank a dashboard whose statistics loaded perfectly well, so the health panel
reports its own state and the rest of the page carries on. The three requests
whose figures the page is built from are asked for together instead, because
they come from the same repository and splitting them would only add a second
failure mode to explain.

### `adminside/src/app/pages/event-edit/event-edit.ts`

#### class `EventEdit`

The "Update a charity event" page, which is the edit half of the write
contract, reached from the list's Edit link, from the dashboard and after a
successful create.
ENDPOINTS
GET  /api/admin/events/:id       the event, whatever its publishing status
(a suspended event must stay editable, and

### `adminside/src/app/pages/event-list/event-list.ts`

#### class `EventList`

The main admin listing, showing EVERY event whatever its status, with the three
actions the brief asks for.
ENDPOINTS
GET    /api/admin/events       the list feature. The admin view is what makes
this page different from the public one: active,
past, suspended and cancelled events all appear,
with their registration and ticket counts.
DELETE /api/events/:id         204 on success. A 409 means the event already

preselect a filter.
THE TOTALS ROW
Every figure in it comes from the API's own per-event columns
(`registrationCount`, `ticketsSold`, `raisedAmount`, `goalAmount`) rather
than from counting anything in the browser: the browser only ever sees the
page of events it was given, so a count derived from the DOM would silently
become a count of the rows that happen to be on screen. It is summed here
only because the row is a total of THIS list, and the two money figures are
restricted to the published rows so that they equal the dashboard's own
totals for the same data - see totalRaised(), which is where that rule and
the reason for it are written down. Sums are rendered with the shared
formatCurrency, the same formatter the dashboard's money tile uses, so a
figure does not read one way on this page and another way there.
THE TOTALS ROW SAYS WHAT IT COVERS
Both money lines are narrower than the table above them, which cannot be seen
from the figures alone. The registrations page's footer solves exactly that
problem with a note under its totals row (`registrations.totalScope`), so the
GOAL line here carries one too (`events.totalGoalScope`) - and it is the line
that needs it most, because the public home page publishes a funding goal as
well. On the seeded data that card reads $197,000 ("Current funding goal",
`stats.activeGoal`) and this cell reads $300,000, and the two are not meant to
be the same number: the card counts the goal of the events that have not
finished, this cell counts the goal of every published event, including the
ones that have (see totalGoal()). Neither computation is changed; each figure
states its own scope in words.

### `adminside/src/app/pages/registrations/registrations.ts`

#### class `Registrations`

The page listing every registration recorded in the system, newest purchase
first.
ENDPOINTS
GET    /api/registrations      the list. It accepts ?eventId and ?keyword, so
both filters are applied by the API rather than
by filtering a page of results in the browser -
which would silently miss rows beyond the page.
GET    /api/admin/events       the options for the event filter. Requested
separately so a slow event request cannot hold
up the registrations themselves.
DELETE /api/registrations/:id  remove one registration.
WHY THIS PAGE IS WORTH HAVING
The brief's data-integrity rule is that an event with registrations cannot be
deleted. Without a page like this the rule is a dead end: staff who genuinely
need to remove such an event have no way to see or clear what protects it.
This is where the rule becomes workable, and the Edit link on every row goes
straight to the event the registration belongs to.
PAGING, AND WHY THE API DOES IT RATHER THAN THIS PAGE
The page asks the API for ONE page of `PAGE_SIZE` rows at a time - `limit` plus
`offset` - and takes the size of the matched set from `meta.total`, which is what
makes the three numbers on the page tell the same story once a filter matches
more rows than a single request can carry. It used to ask for `limit: 100` and
slice that one response in the browser, and past 100 matches the page then
contradicted itself: the count line read "Showing 10 of 250" above a pager whose
ten buttons could only reach page 10, while the footer totalled the 100 rows it
happened to hold under a label claiming to describe the matched set. Paging
through the API is the smaller honest fix here: the wording alternative ("the
first hundred of however many matched") needs a new sentence in four shared
dictionaries, and this needs none. The cost is one request per page change
instead of one per filter change, and the page's own spinner while that request
lands - `loading` already covered "a list request is in flight", and now a page
change is one.
What that means for the figures, stated plainly: `total()` is the API's count of
every row the filters matched and is what `pageCount()` is derived from, so the
pager can reach the last match; the rows in hand are the rows of the current API
page, and totalTickets(), totalValue() and the `registrations.totalSummary` label
describe exactly those rows - the same rows the table above the footer is
showing. A footer that claimed to total the whole matched set could only be
honest if the whole set were in the browser, and the API publishes no whole-set
ticket total (its own `meta.ticketsSold` sums the page it returns).
THE TWO MONEY FIGURES, AND WHY THEY ARE NOT RECONCILED
This page's footer totals TICKET SALES for the rows of the page on screen, and
the dashboard's "Total raised" tile shows `totalRaised` from GET /api/stats.
They disagree - $20,575 against $99,290 over the whole seed - because they
measure different things, and the disagreement was verified against the running
API before anything was written on the page:
GET /api/registrations   each row carries `ticketPrice` and `totalAmount`,
and `totalAmount` is ticketsPurchased x ticketPrice
as the API computes it (repository.local.ts
toApiShape, the mirror of the same expression in
repository.mysql.ts). Summed over the 20 seeded
rows: 49 tickets and $20,575 of TICKET SALES. Those
twenty rows are now two pages of ten, so page one's
footer shows the first half of that sum: the figure
is unchanged, but the page no longer presents a
ten-row total as if it were the set's.
GET /api/stats           `totalRaised` is the sum, over the public events, of
each event's `raisedAmount`, and `raisedAmount` is
the sum of that event's DONATIONS (repository.local
.ts decorate(); MySQL reads the same figure as
SUM(vw_public_events.raised_amount)). $99,290.
The two endpoints agree on the counts - `registrations: 20` and
`ticketsSold: 49` on /api/stats are exactly the 20 rows and 49 tickets
/api/registrations returns across its pages - so nothing is double-counted or
missing; the money is simply two different kinds of income. Neither computation
is changed here, and the page still states its own scope in words under the
totals row (`registrations.totalScope`), because a reader comparing the two
figures has no way to know that from the numbers alone.

### `adminside/src/app/shared/confirm-dialog/confirm-dialog.ts`

#### class `ConfirmDialog`

The "are you sure?" step in front of anything that cannot be undone: deleting
an event, deleting a registration.
WHY NOT window.confirm()
It is one line, but it cannot be styled, it cannot show the extra context a
blocked delete needs (the event's name, how many registrations protect it),
and some embedded browsers suppress it entirely. The archived admin site
built its own dialog for exactly these reasons; this is that dialog expressed
as a component.
The dialog is CONTROLLED BY ITS PARENT: the page renders it only while there is
something to confirm, and listens to the two outputs. That keeps the
destructive action and the thing it destroys in one place, which is easier to
follow than a promise-returning helper.
Access: role="dialog" + aria-modal, Escape cancels, focus starts on Cancel so a
stray Enter cannot delete anything, Tab is kept inside the panel (aria-modal is a
claim that the page behind is covered, and onKeydown is what makes it true), and
clicking the backdrop cancels. The element that opened the dialog gets the focus
back when it closes, so a cancelled delete leaves the keyboard where it was.

### `adminside/src/app/shared/event-form/event-form.ts`

#### class `EventForm`

The event form itself: the ONE form used by both "Add a charity event" and
"Update a charity event", rendered once and driven by the definition in
app/core/event-form.ts.
WHY ONE COMPONENT FOR BOTH PAGES
This is the same decision the archived admin site made with
admin/js/event-editor.js, and for the same reason: adding a field to the
create form must add it to the edit form, and the validation rules must
literally be the same code. The two pages differ only in what they do with
the submitted payload (POST vs PUT) and in a handful of labels, which is what
the `mode` input decides.
WHAT IT DOES
* paints every field of the write contract with its own message slot,
* validates continuously and BLOCKS submission while anything is missing - the
brief asks for this explicitly ("the form must not submit until all required
fields are filled"). Blocking happens in onSubmit(), not by disabling the
button: a disabled button cannot explain itself, while this one marks every
field, prints the reason under each of them and scrolls to the first one,
* shows the API's own per-field 400 messages next to the fields they name
(the `serverErrors` input carries fieldErrorMap from ApiError),
* embeds the live Open-Meteo forecast preview for the chosen venue and date.
It never calls the API itself: it emits an EventInput and the page decides
whether that becomes a POST or a PUT. That is what keeps the same component
usable for two different endpoints.

### `adminside/src/app/shared/weather-preview/weather-preview.ts`

#### class `WeatherPreview`

The live Open-Meteo forecast for the venue and date the administrator has
chosen - the optional external API from Assessment 3, shown BEFORE the event
exists in the database.
WHY THIS DISTINGUISHES THE ADMIN FORM FROM A PLAIN CRUD FORM
A create/edit form only needs the database. This panel needs a second, public
API: the venue's latitude/longitude (which GET /api/admin/reference-data
returns) plus the event date are turned into a `WeatherTarget`, and
WeatherService.forecastFor() asks Open-Meteo for exactly that day at exactly
those coordinates. The staff member can therefore see that a beach fun run
is forecast to be wet on the day, and move it, while it is still a draft.
IT MUST NEVER BREAK THE FORM (the important part)
A venue with no coordinates (the "Online" pseudo-venue), a date beyond
Open-Meteo's 16-day window, a machine with no internet or a slow answer must
not stop an event from being created. WeatherService.forecastFor() therefore
resolves `null` instead of rejecting, and this component renders one of FOUR
states - nothing chosen yet, loading, a forecast, or "not available" - and
never an error.
The first of those four is a review item rather than a nicety: before a venue
and a date exist there is nothing to be unavailable ABOUT, and opening on the
two-sentence "no forecast is available..." note made a working form look
broken. `nothingChosen` below is what separates the two, and it is tested
before `loading` and before the note - see the branch order in the template.
Re-fetching: the target arrives as a signal input, and `toObservable` +
`switchMap` means a change of venue or date cancels the request in flight and
issues the new one, so a slow answer for the old venue can never overwrite the
forecast for the new one.

### `api/src/db/event_db.ts`

#### function `getPool`

Create (once) and return the shared pool.
The `error` listener is registered through a narrow local cast because
mysql2's own typings list only the pool's lifecycle events.
- `@returns The process-wide pool, creating it on the first call and reusing it afterwards.`

#### function `query`

Run a parameterised SQL statement.
ALWAYS pass user input through `params` - never build SQL by string
concatenation. mysql2 escapes every value in `params`, which is what
prevents SQL injection on the search endpoint.
- `@param sql - The SQL text, containing "?" placeholders.`
- `@param params - The values bound to the placeholders. May be omitted for a statement that takes none.`
- `@returns The rows for a SELECT, or the result header for an INSERT or UPDATE.`

#### function `transaction`

Run `work` inside a database transaction.

Used by the event delete rule, which must decide and act as one unit.
- `@param work - The callback that does the work, given the connection to run on.`
- `@returns Whatever `work` returned, once the transaction has committed.`

Used by GET /api/health so a marker can confirm the setup in one click, and by

- `@returns A report of the connection, the server version, the table count, and`

#### function `close`

Close the pool, used on shutdown and after the test suite.
The module-level handle is cleared before awaiting `end()`, so a second call
(or a `query()` racing the shutdown) creates a fresh pool instead of using one

#### function `describe`

Expose the settings for diagnostics.
The password is deliberately omitted, so this can be logged or returned by a

- `@returns The host, port, user, database and connection limit in use.`

### `api/src/middleware/errorHandler.ts`

#### function `notFound`

Answer 404 for any URL that no route matched.
It is registered after every route, so reaching it means nothing claimed the
request. The reply names the method and the URL so a mistyped endpoint is
obvious from the response body alone, and the hint points at the endpoint
index rather than leaving the caller to guess.
- `@param req - The request that matched no route; its method and URL are quoted in the message.`
- `@param res - The response the 404 envelope is written to.`
- `@param next - Accepted so Express recognises a four- or three-argument`
middleware, but never called: this handler always writes the response.

#### function `errorHandler`

Convert anything thrown into the API's single error envelope.
It must keep four arguments for Express to treat it as an error handler, so
`next` is declared but unused even though the chain ends here. The status is
taken from the thrown value when it looks like an HTTP status and otherwise
becomes 500, and unexpected failures are logged with their full stack while
the client receives only the message, so internal details are not leaked.
WHY THERE IS NO 500 FACTORY ON `HttpError`
`HttpError` used to carry a `serverError()` builder beside `badRequest()`,
`notFound()`, `conflict()` and `tooManyRequests()`, and nothing ever threw
it: no service, repository, validator or middleware called it, so the 500
below was the only path a server-side failure could take. The builder was
therefore removed rather than kept as a factory with no caller, and the one
decision it documented - that in production the message of any 500 is
REPLACED rather than passed through, so internals are never leaked - is
recorded here, at the branch that actually reads `IS_PRODUCTION`.
- `@param error - The thrown value: an HttpError, a mysql2 driver error, or anything else.`
- `@param req - The request being answered, used for the log line and to know whether the response is still open.`
- `@param res - The response the error envelope is written to.`
- `@param next - Required so Express registers this as an error handler; never called.`

### `api/src/middleware/security.ts`

#### interface `RateLimiter`

The rate limiter is a RequestHandler, and nothing more than one.
It used to declare a `stop()` that cleared its pruning interval, on the
reasoning that an interval would keep a test runner or a shutting-down
process alive with no way to silence it between cases. That reasoning was
solved at the source instead: the interval is `unref()`'d (see
`createRateLimiter` below), so it never holds the process open and there is
nothing left to stop. No test, tool or caller in the repository ever used
the method, so it was removed here rather than left as a promise the type
made and the implementation could drop at any time.

#### function `securityHeaders`

Set the security headers that suit a JSON API.
`X-Content-Type-Options: nosniff` stops a browser from reinterpreting a JSON
body as HTML, `X-Frame-Options: DENY` blocks clickjacking through an embedded
frame, and the referrer policy stops URLs (which carry ids) leaking to third
parties. The resource policy is `cross-origin` rather than `same-origin`
because the two Angular sites are served from a different port to the API in
development.
- `@param req - The incoming request; unused, but part of the middleware contract.`
- `@param res - The response whose headers are stamped.`
- `@param next - Passes control to the next middleware in the chain.`

#### function `createCors`

Build the CORS middleware from the configured origin list.
`CORS_ORIGIN` is a comma separated list, and `*` means any caller, which is
the development default. When an explicit list is configured the matching
origin is echoed back instead, together with `Vary: Origin`: without that
header a shared cache could hand one site's response to another. The exposed
header list is what lets the Angular client read the `Location` of a freshly
created resource, and the ten-minute preflight cache keeps the update and
delete forms from paying for an extra round trip on every click.
- `@returns The CORS middleware, which answers a preflight with 204 and a bare body.`

#### function `createRateLimiter`

Build the fixed-window rate limiter keyed by client IP.
A window is chosen over a dependency so the marker can read and understand
the logic; the counter resets on a timer rather than on a rolling basis, which
is the trade-off a small API can afford. The limiter keys on `req.ip`, which
is why server.ts trusts exactly one proxy hop and no more - trusting every hop
would let a caller forge `X-Forwarded-For` and never be limited. Over the
limit the failure is raised as an `HttpError`, so it leaves through the same
error middleware as every other failure. A `RATE_LIMIT_MAX` of zero or less
disables the limiter entirely, which the test suite and local demos rely on.
- `@returns The limiter itself, ready to mount on the app with `app.use()`.`

### `api/src/repositories/registration.repository.local.ts`

#### function `toApiShape`

Convert one raw row into the API shape used by both data sources.
The conversion happens in exactly one place so the two repositories cannot
drift apart; the tier price and the event name are looked up rather than
stored, so a registration always reports the current tier name and price.
- `@param row - The raw registration row in the snapshot's snake_case shape.`
- `@returns The registration as the API returns it, including the computed total amount.`

#### function `maskAttendeeName`

Mask an attendee's name as "Grace T.".
A first name plus the initial of the surname identifies the row to the person
who booked it - "yes, that is my registration" - without publishing a full
identity next to a ticket count and a date, which is what turns a booking list
into a list of contactable people. A single-word name is shown as it is, and an
empty name yields an empty string so the caller can fall back to the
registration id rather than rendering a blank cell.
The public page renders this inside the registrations table
key, so the words around it are translated while the name itself is data.
- `@param attendeeName - The name as the registration stored it, or null when the row carries none.`
- `@returns The masked name, for example "Grace T.", or an empty string when no name was stored.`

#### function `narrowRegistrationToPublic`

Replace an attendee's contact details with the masked line the public page shows.
WHY THIS EXISTS
The offline mirror is the twin of repository.mysql.ts, so it must enforce the
same privacy rule that the narrower SELECT enforces there: `attendee_email`
and `attendee_phone` are personal information, and the public event detail
endpoint answers an anonymous visitor whose page renders whatever it receives.
Publishing a named person's full email address and mobile number on a public
page breaches the Australian Privacy Principles (APP 3 and APP 11 - collect
and disclose only what the purpose needs).
The two keys are DELETED rather than blanked, so the response shape is
identical to the MySQL one: `'attendeeEmail' in row` is false in both, which
is exactly what the test suite asserts. This is a data-minimisation boundary
rather than a display decision - a template can be changed tomorrow, a row
that never left the database cannot - which is why it lives beside the query
it mirrors instead of in the controller.
The admin path (GET /api/admin/events/:id) does NOT pass through here: staff
keep the whole row, because they need the contact details to run the event.
- `@param row - One registration in the API shape, as toApiShape() produced it.`
- `@returns A copy of the row without attendeeEmail and attendeePhone, carrying attendeeDisplayName ("Grace T.") instead.`

### `api/src/repositories/repository.local.ts`

#### function `today`

"Today" for the derived event state.
DATA_SOURCE=local + DEMO_TODAY=2026-09-28 makes the demo reproducible; when
DEMO_TODAY is not set the real current date is used, matching CURDATE().
db/event_db.ts pins the MySQL session clock to the same value, so CURDATE()
answers the same day when DATA_SOURCE=mysql and the suite is pinned too.
That date is the HOST'S LOCAL date, not the UTC one. CURDATE() answers in the
database server's own time zone, which on the deployment host is local time,
so taking the UTC date here made the two data sources disagree for the first
ten or eleven hours of every day on a UTC+10 host - an event happening today
was "upcoming" offline and "ongoing" in MySQL. Building the string from the
local getters is what makes the mirror answer what CURDATE() answers.

### `api/src/repositories/repository.mysql.ts`

#### function `escapeLike`

Escape the LIKE metacharacters in a value that is bound to a LIKE pattern.
A keyword or a city is user text, so a `%` or a `_` in it has to match itself
rather than act as a wildcard: `?keyword=%` would otherwise build `LIKE '%%%'`
and return every row, and `?keyword=_` every row with at least one character,
while the offline mirror - whose `includes()` is literal - returns nothing for
the same request. Escaping in one place, used by every LIKE in this file, is
what keeps the two data sources answering the same question.
- `@param value - The raw search text, exactly as the client sent it.`
- `@returns The text with `\`, `%` and `_` backslash-escaped, ready to be wrapped in `%` signs.`

#### function `containsPattern`

Build the bound value for a contains-search on one column.
The single place a LIKE pattern is assembled, so no call site can forget
either the escaping or the surrounding wildcards.
- `@param value - The raw search text, exactly as the client sent it.`
- `@returns The `%escaped%` pattern to bind to a `LIKE ? ESCAPE '\\'` condition.`

#### function `buildEventFilter`

Build the WHERE / HAVING fragment used by every event listing.
All user input is bound through `params`; even the sort column is whitelisted
rather than interpolated into the SQL text, which is what keeps a filter value
like `%' OR 1=1 --` inert. The state filter goes into HAVING rather than WHERE
because `eventState` is derived by the view and cannot be tested before the row
is assembled.
- `@param filters - The validated filters from the service layer. May be omitted, in which case no condition is added.`
- `@returns The WHERE and HAVING fragments, empty when nothing was filtered, plus the values to bind to them.`

#### function `REGISTRATION_COLUMNS`

The registration columns shared by the read queries that serve STAFF.
The joined form is used wherever the tier name, the price and the event name
are needed; the amounts are computed in SQL so both data sources report the
same total for a registration.
This projection carries `attendee_email` and `attendee_phone`, so it must only
ever be selected for the admin routes. The public counterpart is
REGISTRATION_COLUMNS_PUBLIC below, and the two differ on purpose - see the
privacy note there before adding a caller.

#### function `REGISTRATION_COLUMNS_PUBLIC`

The registration columns for the PUBLIC endpoints: the same rows, MINUS the
attendee's email address and phone number, PLUS the masked backer name that
replaces the full one.
WHY THIS PROJECTION EXISTS AND MUST NOT BE "COMPLETED"
`attendee_email` and `attendee_phone` are personal information. The public
event detail endpoint answers an anonymous visitor, and the page renders the
rows it returns, so selecting those two columns published a named person's
full email address and mobile number on a public web page - a breach of the
Australian Privacy Principles (APP 3 and APP 11: collect and hold only what
the purpose needs, and do not disclose it). They are therefore NOT selected
here, so no later change to the template, the client or the serialiser can
put them back on the page: the data never leaves the database.
A future reader adding a column to this list must keep that rule. If a screen
genuinely needs an attendee's contact details, it is a staff screen and it
must read the admin endpoint (GET /api/admin/events/:id), which asks for
REGISTRATION_COLUMNS above - never this list.
WHY THE BACKER NAME IS DERIVED HERE RATHER THAN SENT RAW
The public page still has to say who a registration belongs to, and it shows
a masked backer line ("Grace T."). That line is derived in SQL - the CASE on
attendeeDisplayName below - rather than shipping `attendee_name` and masking
it in the page, for the same reason the two contact columns are not selected:
a response that never carried the full name cannot publish it, whatever a
template, a client or a future export later renders. Masking on the way out
of the database is a data-minimisation boundary, not a display decision.
The CASE is the twin of maskAttendeeName() in
registration.repository.local.ts, and it has to reproduce it exactly: an
empty or whitespace-only name masks to an empty string, a single word is
returned unchanged, and anything longer keeps the first word and the
upper-cased initial of the last word followed by a full stop. Only the
offline twin can be run by the suite here, so tests/run-tests.js reads this
CASE back out of this constant and compares the two on the same inputs.
The admin projection above is deliberately NOT masked, and neither is the
write read-back in registration.repository.mysql.ts: staff need the whole
name and both contact details, and the offline twin keeps them raw in exactly
the same places.
Everything the public page legitimately needs is still here: the attendee's
masked name, how many tickets they bought, the tier they bought and when.

#### function `registrationQueries`

The registration reads the merged repository publishes as `registrationQueries`.
They live on the read half because MySQL keeps every registration read here;
the offline twin keeps its reads and writes in one module instead, which is why
src/repositories/index.ts publishes this member only when the read half does
not already carry it.

### `api/src/repositories/write.repository.mysql.ts`

#### function `toColumns`

Map the camelCase keys of a validated payload onto database columns.
Only the keys that are actually present are emitted, which is what makes an
update partial: an absent key means "leave this column alone" rather than
"write its default". The mapping is explicit rather than derived from the key
name so that the API's vocabulary and the schema's cannot drift apart silently.
The mapping is also the whole list of columns an administrator may set, in
table order: nothing outside it can be written, so a request cannot set a
column the form does not offer - an id, a timestamp or a computed column.
- `@param values - The validated values from the write service.`
- `@returns The column names to write and the values to bind to them, in matching order.`

#### function `translateMysqlError`

Turn a mysql2 driver error into the HTTP error the client should see.
Only the cases a member of staff can actually cause are translated; anything
else is re-thrown and becomes a 500 with a stack trace in development. The
`context` object carries the names the message needs (an event name, a
registration count) because the driver error alone does not know them.
`sqlMessage` IS DELIBERATELY NOT FORWARDED. It used to ride along in
`details`, which published the schema to the client: a duplicate tier name
answered with the constraint, the table and the raw key - "Duplicate entry
'14-seat' for key 'ticket_types.uq_ticket_event_name'". A UI cannot use that,
it contradicts the offline twin (which sends the offending tier name and a
hint instead), and it hands an attacker the exact index names to aim at. The
driver's own text is left on the error, which the error middleware logs for a
5xx; a failure the client can act on is described in words instead.
- `@param error - The value the driver rejected with, in any shape it uses.`
- `@param context - Extra facts for the message, such as the event name or the registration count. May be omitted.`
- `@returns The matching HttpError, or `null` when the code is not one this layer explains.`

#### function `replaceTicketTypes`

Add the tiers for an event, unless it already has some.
This is the published `replaceTicketTypes` contract and the path updateEvent()
uses, so it keeps its own transaction: the existence check and the inserts are
one unit, and a failure half way through cannot leave an event with one of its
three tiers. A failure is logged and swallowed rather than rethrown, because
here the event itself has already been saved and losing the tiers is not a
reason to tell the client the update failed; a driver error that this layer
can explain (an unknown reference, a value the column refuses, a duplicate
tier name) is still raised as an HttpError, which is the same answer the
offline twin gives. insertEvent() deliberately does NOT come through here: a
create must fail as a whole, so it calls insertTicketTypes() inside its own
transaction instead.
The "unless it already has some" guard is what makes this the same call in
both data sources; write.repository.local.ts now returns early for an event
that already has tiers too, where it used to append a second set.
- `@param eventId - The event the tiers belong to.`
- `@param ticketTypes - The validated tiers to insert, each with a name, a price and optional quantity and description.`

### `api/src/services/eventService.ts`

#### function `buildQuery`

Turn raw req.query into { filters, paging } or throw HttpError(400).
Every value is checked here rather than in the controller, because the same
filters have to be produced for both data sources and for the admin and public
views. A problem is collected rather than thrown on the spot, so one 400 can
list every bad parameter instead of only the first.
Supported parameters
category, categoryId  one or many ids (repeat the key or use commas)
location, locationId  one or many location ids
city                  partial city name
date                  a single day (YYYY-MM-DD)
from, to              a date range (YYYY-MM-DD, inclusive)
state                 upcoming | ongoing | past | all
keyword               free text search
organizationId        restrict to one organisation
isFree                true | false
includePast           true | false (used by the home page)
sort, direction       whitelisted sort keys
limit, offset, page   pagination
audience              public | admin (the A3 admin switch), checked like
`state` and `sort`: a value outside the list is a 400
rather than a switch that is quietly ignored
publishStatus         active | suspended | cancelled | all, checked like `state`
and `sort`: a value outside the list is a 400 rather than
a filter that is quietly ignored
- `@param query - The untrusted query string. May be omitted, in which case the defaults describe the next upcoming events.`
- `@returns The validated filters and the paging values derived from them.`
- `@throws HttpError with status 400 when any parameter cannot be understood, carrying the per-parameter list.`

#### function `searchEvents`

List the events matching a query string, for the home page and the search page.

- `@throws HttpError with status 400 when the query string is not valid.`

#### function `listActiveEvents`

Listing for the home page: everything that has not finished yet.
The state is pinned to `upcoming` rather than defaulted, so a caller cannot
turn the home page listing into a history listing with `?state=past` or
`?state=all` - the pinned value overwrites whatever arrived. The documented
`?includePast=true` alias still widens it, because that alias is folded into
the state below as `all`; that is deliberate rather than an oversight, since

- `@param query - The untrusted query string. May be omitted, in which case the default page of upcoming events is returned.`

#### function `getEventById`

- `@returns The event, with its ticket tiers and progress figures.`
- `@throws HttpError with status 400 when the id is not a positive whole number.`
- `@throws HttpError with status 404 when no event matches, or when the only match is not active and `status` was not widened.`

#### function `listAllEvents`

### `api/src/services/registrationService.ts`

#### function `createRegistration`

Register one attendee for one event.
The remaining allocation is checked before the insert (rule 3), and the
repository's unique key is the final authority on rule 1 - the check here
gives a readable 409 in the ordinary case, and the key still refuses a second
registration if two requests race.
- `@param rawEventId - The event id from the route parameter, still unvalidated text.`

#### function `updateRegistration`

Update one registration as a partial update.
Only the fields sent are changed, and sending `{}` is a 400 rather than a
silent success, because a client that sent nothing has almost certainly made a
mistake. Changing the email is re-checked against the event's unique key by
the repository, so a move onto an address that is already registered is a 409.
The allocation rule from a create applies here too: raising `ticketsPurchased`,
or moving the row onto a different tier, is checked against the tier's
remaining allocation before anything is written. The row's own tickets are
excluded from that count, so an update that keeps the quantity it already has
is never refused - which is what makes a partial update of only the notes, or
a re-send of the current quantity, still succeed for a tier that is sold out.

missing id is a 404 at that point rather than after the check, so an unknown
id is never reported as an allocation problem.

- `@param body - The untrusted request body holding only the fields to change.`
- `@returns The registration as it now stands.`
- `@throws HttpError with status 400 for an invalid id, an empty body, a ticket count the tier cannot satisfy or a value the database refuses, 404 when no registration has that id, and 409 when the new email is already registered for that event.`

### `api/src/utils/asyncHandler.ts`

#### type `AsyncRequestHandler`

An async route handler: it may return a promise, or nothing at all.
The union with `unknown` is deliberate: a route that never awaits anything is
still a valid handler, so both shapes are accepted and no caller has to mark a
handler `async` purely to satisfy the type. `Req` and `Res` default to
Express's own `Request` and `Response`, and are narrowed only where a route
needs a typed body or query.

#### function `asyncHandler`

Wrap an async route handler so its rejection reaches the error middleware.
`Promise.resolve(...)` is applied to the handler's result rather than
`await`-ing it inside a `try`/`catch`, so a handler that returns a plain value
costs nothing extra, and a handler that returns a promise has its rejection
routed to `next` on the microtask queue - which is what stops Express from
treating the request as still in flight.
- `@param handler - The route handler to wrap; it may return a promise or a plain value.`
- `@returns A `RequestHandler` that never rejects, so it can be passed straight`
to `router.get()` and friends.

### `api/src/utils/errors.ts`

#### class `HttpError`

An error carrying the HTTP status the caller should send back.
Extending `Error` rather than returning a result object is what lets the
service layer `throw` a 400 or a 409 and have it unwind through exactly the
same path as an unexpected database failure, so there is one response shape to
maintain. The middleware reads `status` and `details` off whatever it is
handed, so this class is the contract between the two layers.

### `api/src/utils/validators.ts`

#### function `parseIdList`

Split repeated and comma separated parameters into a clean list of ids.
This is what allows the client to send either
?category=1&category=2      (repeated)
?category=1,2               (comma separated)
?category[]=1&category[]=2  (PHP style brackets)
and is the single reason the three forms behave identically. Duplicates are
collapsed and anything that is not a positive whole number is reported as a
problem rather than silently dropped, so a typo in a filter never widens the
result set.
- `@param value - The raw query value in any of the three accepted forms.`
- `@param fieldName - The query parameter name, used in the error message the client displays.`
- `@param errors - The shared problem list that this helper appends to.`
- `@returns The distinct valid ids, in the order first seen; empty when none were usable.`

#### function `isValidDate`

Test whether a value is a real calendar date in `YYYY-MM-DD` form.
The regular expression alone would accept 2026-02-31, so the value is also
parsed and formatted back: only a date that survives the round trip is real,
which is what stops an impossible date reaching the database.
- `@param value - The value to test, normally a string from a query or a body.`
- `@returns `true` when the value is a genuine date, `false` for anything else.`

#### function `parseInteger`

Parse a positive integer and check it against a bounded range.
The options object carries `min` (default 1), `max` (default
`Number.MAX_SAFE_INTEGER`) and the shared `errors` array; a value outside the
range is reported and `undefined` comes back so the caller can fall back to
its default. Fractions and non-numeric text are refused here rather than
being rounded, because `LIMIT 2.5` and `LIMIT 'abc'` would otherwise reach the
query builder.
- `@param value - The raw value from a query string.`
- `@param fieldName - The query parameter name, used in the error message.`
- `@returns The number when it is a whole number inside the range, otherwise `undefined`.`

#### function `parseText`

Read a single trimmed string, treating an empty string as absent.
An empty value is treated as absent rather than as a value, so a cleared
search box means "no keyword" instead of "keyword is empty".
- `@param value - The raw value, which may be a list if the parameter was repeated.`
- `@returns The trimmed text, or `undefined` when there was nothing to read.`

#### function `requiredDate`

Read a real calendar date out of a request body.
This begins the Assessment 3 group of body helpers. Query strings and JSON
bodies arrive in different shapes, so every helper below takes the whole
`body` plus a shared `errors` array and reports every problem at once instead
of failing on the first one; the service layer turns the collected array into a
single HTTP 400 with a per-field list, which is what both websites display. A
full ISO timestamp is accepted and reduced to its date part, which is what an
`<input type="date">` or a Postman timestamp sends, and the options object
controls whether the field is mandatory (`required`, default `true`).
- `@param body - The untrusted request body being validated.`
- `@param field - The body field name, used in the message and as the error's field.`
- `@param errors - The shared problem list that this helper appends to.`
- `@returns The date in `YYYY-MM-DD` form, or `undefined` when it is absent or invalid.`

#### function `requiredTime`

Read a clock time out of a request body.
A bare `HH:MM` is widened to `HH:MM:SS` because the `TIME` columns carry
seconds, so storing the value the client typed keeps the column's own format.
The options object controls whether the field is mandatory (`required`,
default `true`).
- `@param body - The untrusted request body being validated.`
- `@param field - The body field name, used in the message and as the error's field.`
- `@param errors - The shared problem list that this helper appends to.`
- `@returns The time in `HH:MM:SS` form, or `undefined` when it is absent or invalid.`

#### function `requiredText`

Read a non-empty piece of text out of a request body.
The options object carries `required` (default `true`), `min` (default 1) and
`max` (default 5000). The upper bound matches the widest `VARCHAR` in the
schema, so a value that would be silently truncated by the database is
refused here with a message the form can display.
- `@param body - The untrusted request body being validated.`
- `@param field - The body field name, used in the message and as the error's field.`
- `@param errors - The shared problem list that this helper appends to.`
- `@returns The trimmed text, or `undefined` when it is absent, blank or out of range.`

#### function `requiredNumber`

Read a number out of a request body.
The options object carries `required` (default `true`), `min` (default 0),
`max` (default `Number.MAX_SAFE_INTEGER`) and `integer` (default `true`). The
distinction between a whole number and a decimal exists because the schema
mixes `INT` columns with the decimal price columns, so one helper serves
both; the range check mirrors the column's own range where the caller passes
one.
- `@param body - The untrusted request body being validated.`
- `@param field - The body field name, used in the message and as the error's field.`
- `@param errors - The shared problem list that this helper appends to.`
- `@returns The number when it is inside the range, otherwise `undefined`.`

#### function `requiredBoolean`

Read a boolean out of a request body.
A JSON body carries a real boolean, but an HTML form or a Postman form posts
the strings `true`, `false`, `1`, `0`, `yes` and `no`, so all of them are
accepted rather than forcing every caller to normalise first. The options
object carries `required` (default `false`) and `fallback`, which is returned
when the field is absent - the flag columns are optional, so the fallback is
usually the schema default.
- `@param body - The untrusted request body being validated.`
- `@param field - The body field name, used in the message and as the error's field.`
- `@param errors - The shared problem list that this helper appends to.`
- `@returns The boolean when the value was understood, the fallback when it was absent, otherwise `undefined`.`

#### function `requiredEnum`

Read a value from a fixed list out of a request body.
The comparison is case-insensitive and the accepted spelling is returned in
lower case, so `Published` from a hand-written request and the `ENUM` value in
the schema agree; the error message lists the allowed values, which is what the
admin form shows beside the field. The options object carries `required`
(default `true`) and `fallback`, returned when the field is absent.
- `@param body - The untrusted request body being validated.`
- `@param field - The body field name, used in the message and as the error's field.`
- `@param allowed - The permitted values, in the order they should be listed in an error.`
- `@param errors - The shared problem list that this helper appends to.`
- `@returns The matching value in lower case, the fallback when absent, otherwise `undefined`.`

#### function `requiredId`

Read a referential id out of a request body.
This is `requiredNumber` with the range pinned to a positive whole number, so
a foreign key of 0 or a negative id is refused before the database has to
reject it; whether the row exists is the repository's business, checked when
the insert or update runs. The options object controls whether the field is
mandatory (`required`, default `true`).
- `@param body - The untrusted request body being validated.`
- `@param field - The body field name, used in the message and as the error's field.`
- `@param errors - The shared problem list that this helper appends to.`
- `@returns The id when it is a positive whole number, otherwise `undefined`.`

#### function `requiredEmail`

Read an email address out of a request body.
The length is capped at 150 characters, matching the column and the database
`CHECK` constraint, and the pattern is deliberately the pragmatic
`something@something.something` test: it accepts every address a real user
types while rejecting the obvious mistakes, which is the check the form can
act on. The options object controls whether the field is mandatory
(`required`, default `true`).
- `@param body - The untrusted request body being validated.`
- `@param field - The body field name, used in the message and as the error's field.`
- `@param errors - The shared problem list that this helper appends to.`
- `@returns The address in its trimmed form, or `undefined` when it is absent or malformed.`

#### function `throwIfInvalid`

Throw a single HTTP 400 carrying every collected field error.
This is the point where the collect-then-report helpers above become a
response: one 400 with a per-field list, rather than the first problem only.
The require of `./errors` is lazy because `errors.ts` does not import this
module, so the cycle is avoided by loading it at throw time.
- `@param errors - The collected problems; an empty list means the request was valid.`
- `@param message - The summary returned alongside the field list. May be`
omitted, in which case a generic invalid-fields message is used.
- `@throws HttpError with status 400 when `errors` is not empty, carrying the list as `details`.`

### `clientside/src/app/app.routes.ts`

#### const `routes`

The public website's routing table.
Every page is lazy, every title is a translation key carried in route data, and
a bare /register deliberately falls through to the 404.
- `@file Routing for the CLIENT-SIDE website.`
WHY EVERY PAGE IS LOADED WITH `loadComponent`
The legacy site was four separate HTML documents, so a visitor only ever
downloaded the code for the page they asked for. A single-page application
bundles everything together by default, which would undo that. `loadComponent`
with a dynamic `import()` keeps the same property in Angular: the home page's
bundle does not contain the search form, the registration form or the
registrations table, and each one is fetched the first time its route is
visited. It also means none of these components is referenced from anywhere
else, so the bundler can prove the split is real.
WHY `title` IS A TRANSLATION KEY IN `data` AND NOT THE ROUTER'S OWN `title:`
This table used to carry both: a `data.titleKey` AND a hard-coded English
`title:` string. The English one won. `DefaultTitleStrategy.updateTitle()` is
called by the router AFTER the activated components have been constructed
(it runs once `ActivateRoutes` has finished, immediately after NavigationEnd),
so the page's own `useDocumentTitle().set()` happened first and was then
overwritten. Measured on the built development bundle: with
`title: 'Search charity events | Unity Heart Foundation'` on this route,
/search rendered that English title on a page whose `<html lang>` was
`zh-CN`, while /events/2 was correctly Chinese - its page sets the title a
second time from the API's answer, after the router has had its turn. The
strings were therefore English chrome in all four languages, written in
TypeScript where neither the template check nor the dictionary checks could
see them. Every route now carries ONLY the key in `data`, each page component
resolves it through `Title` + `TranslationService` when it runs - see
`useDocumentTitle()` in `shared/page-title.ts` - and no route sets a static
`title:`, which is what adminside/src/app/app.routes.ts has always done.
WHY THERE IS NO ROUTE FOR 'register' WITHOUT AN ID
Registration is per event, exactly as the legacy page treated it: the event
id travels in the URL. `**` therefore catches a bare /register and shows the
friendly 404 rather than a form that cannot know what it is registering for.

### `clientside/src/app/app.ts`

#### class `App`

The root of the CLIENT-SIDE website: the four segments in order - Header (which
contains Nav), the routed page as Body, and Footer.
WHY THE LAYOUT LIVES HERE RATHER THAN IN A ROUTED LAYOUT COMPONENT
Every route wants the site chrome except for one detail: the wildcard 404 route
shows the language and theme controls (a visitor who mistyped a URL still needs
them) and the footer, but not a menu full of links to pages, so only the menu is
hidden on that one route by inspecting the router's current URL. A layout
component with child routes would be the tidier answer for a larger site, but
here it would add a second `<router-outlet>`, a second level of lazy loading and
a routing table that no longer reads as a flat list of the four pages the brief
asks for.
WHY THE ROUTE URL IS READ THROUGH toSignal
Angular 22 is zoneless: template expressions are re-evaluated when a signal
they read changes. The router is not a signal source by default, so the URL
is projected into one - and `filter` drops every navigation event that is
not a completed one, so the chrome cannot flicker half way through a
navigation.
The 404 page still needs to exist as a route of its own; this component only
decides whether it is framed by the site chrome.
THE SHELL ALSO STARTS THE FRAGMENT WATCHER
`FragmentScrollService` is created here, in the component that lives for the
whole session, so it starts listening before the initial navigation resolves
and stops when the application is torn down. It is not rendered and has no
template: it is the answer to the cross-route fragment link described in its
own file (`clientside/src/app/shared/fragment-scroll.ts`), which arrives
before the home page's listing has rendered and would otherwise come to rest
a thousand pixels short of the section it named.

### `clientside/src/app/layout/settings-bar.ts`

#### class `SettingsBarComponent`

The two settings controls that appear in the header on every page: the
language picker and the theme switch.
Why a component rather than markup copied into the header?
Both controls read and write a service from the shared library
(TranslationService, ThemeService), so keeping them together means the
header template contains navigation only and there is one place that decides
how a language or theme is chosen.
Language picker: all four supported languages, labelled with `nativeLabel`
("English", "中文", "Tiếng Việt", "日本語"). A visitor who cannot read the
current interface language can still recognise their own, which an
English-only label list would not allow. A native `<select>` is used because it
is keyboard accessible and works on a phone without extra code.
Theme switch: one button that CYCLES light -> dark -> system. Three states
cannot be expressed by a two-state switch, and a three-way radio group would
take far more room than the header has. It is drawn as a single round icon
button - a sun while the resolved theme is light, a moon while it is dark - and
its `aria-label` spells out which preference is stored, which matters because
"System" and "Light" look identical when the operating system is light and no
two-state picture can tell them apart. See the markup for the full argument
(review item C2: it used to be an icon plus the words "Theme: Light", 130.80px
of the header's prime space, and it is now about 34px).
NO @angular/forms HERE ON PURPOSE
The select writes straight through to the service with a `change` handler
instead of [(ngModel)]. There is no form to submit and no validation, so a
two-way binding would add a dependency for nothing.

### `clientside/src/app/layout/site-header.ts`

#### class `SiteHeaderComponent`

The site header: the HEADER segment of the four every page shares (Header, Nav,
Body, Footer), holding the brand and the language/theme controls, and rendering
the NAV segment inside its own `<header>` landmark.
WHAT IS IN IT, AND WHAT IS NOT
The brand, the settings bar and the mobile menu button. The menu itself is
`app-site-nav`, a component of its own: see that file for why the three
destinations are Home, Search Events and Admin site, and for why the menu lives
in this header rather than beside it in the shell. The component is rendered
once, above `<router-outlet>`, so it is identical on every page - which is what
the legacy js/nav.js achieved by writing the same markup into every document.
WHY THE HEADER STILL OWNS `showNav` AND `menuOpen`
Both pieces of state describe the header's own controls. `showNav` is the shell's
instruction ("this route does not want a menu") and the header forwards it to the
nav; `menuOpen` is the answer to the hamburger button, which is a child of this
template because that is the position the layout stylesheet gives it. Keeping the
button and the state here, and pushing the result down as an input, means the nav
component holds no state of its own and the two can never disagree. The admin
header forwards `showNav` the same way; it has no menu button, because the admin
menu is always visible, so it has no `menuOpen` either.
WHY THE HEADER MEASURES ITSELF AND PUBLISHES ITS HEIGHT
This header is sticky, so every sticky card in the page under it has to come to
rest clear of its bottom edge. That height USED TO DEPEND ON THE LANGUAGE, and
through two separate lines of the header: the nav labels wrapped onto more
lines once the row ran out of room, and the "interface language only" note was
a full-width second line inside the settings bar that only the three
non-English languages render. Measured in a 1000px-tall window before the fix:
65.31px in English, 85.02px in Chinese at every width; Vietnamese and Japanese
89.63px at 1920 and 1440px, 113.94px at 1100 and 900px, and 211.19px for
Japanese at 900px; at 390px 120.09 / 146.52 / 146.52 / 164.94px. The three
sticky cards used to share a written `top: 96px` derived from the English
height, so at 1024px their top edge came to rest 17.94px (Vietnamese) and
66.56px (Japanese) BEHIND the header.
THE HEIGHT IS NOW THE SAME IN ALL FOUR LANGUAGES: 65.31px at 1920, 1440, 1100
and 900px and 120.09px at 390px, because the labels hold one line at every
width (see the nowrap note on `.site-nav__link`) and the note renders in a band
BELOW this element instead of inside it (see the template). The height is still
read from the real element and written to `--site-header-height` on the
document element (`:root` in clientside/src/styles.css carries the 900px-and-up
fallback used before the first measurement, and the whole before/after table),
and the cards compute their offset from it. A ResizeObserver rather than a
window `resize` listener is what makes the value follow a resize, a font swap
or any other reflow of this row, none of which the window fires an event for -
the language switch no longer changes this element's height at all.

### `clientside/src/app/pages/event-detail/event-detail.ts`

#### class `EventDetailPage`

The event detail page.
ENDPOINTS USED
`GET /api/events/:id`  everything on this page.
WHY ONE REQUEST IS ENOUGH
Assessment 3 extended this endpoint to include the COMPLETE registration list
for the event, so the registrations table (the key A3 requirement) needs no
second call. That is also why there is no spinner inside the table: the rows
arrive with the event itself.
WHY THE REGISTRATIONS TABLE SHOWS A MASKED NAME AND NO CONTACT DETAILS
This page is public and anonymous, so the API does not send an attendee's
email address or phone number with it at all - the keys are absent from the
response, not hidden by a template, because publishing a named person's email
and mobile on a public page breaches the Australian Privacy Principles
(data minimisation). What arrives instead is `attendeeDisplayName`, the masked
backer line ("Grace T."), which lets the visitor who booked recognise their
own row without the page identifying anybody else. The full details still
exist for staff: the admin screens read GET /api/admin/events/:id, which asks
for them explicitly. `backerName()` is the one place this page builds that
label, so there is no second convention to drift.
WHAT THE PAGE MAY SAY ABOUT REGISTRATION
Nothing in the schema is a "registration is open" flag, so the status
sentence and the hero's ticket action are derived from state the page already
has: a past event cannot be registered for, and an event whose every published
tier has sold out cannot be registered for either. Everything else IS taking
registrations now - the register page accepts them - so the page says so
rather than claiming registration has not opened yet, which is what it used to
do while the sidebar offered a working Register button and the table below
listed people who had already booked. The two are computed in one place
(`registrationOpen`) so the sentence, the button and the register control
cannot disagree again.
THE REGISTRATION LIST IS NOT RE-SORTED HERE
The API orders it `registered_at DESC` - "newest purchase first", which is what
the brief asks for. Sorting again in the browser would be a second source of
truth for the same rule, and the two could disagree (a date-only sort in the
browser cannot break a tie between two purchases on the same day, the way the
database's timestamp ordering can). The array is rendered in the order it
arrived.
WHY THE WEATHER PANEL IS ON EVERY EVENT AND CANNOT FAIL
The forecast comes from a third-party API (Open-Meteo) using the venue's
latitude/longitude, which the event response supplies. A venue with no
coordinates ("Online (Australia-wide)"), an event more than 16 days away, or
a machine with no internet must NOT break a page whose real content is the
event. `WeatherService.forecastFor()` resolves `null` for every one of those
cases instead of erroring, so the visitor never meets an error.
Absent is not the same as silent, though, and the panel is no longer
conditional. It used to be wrapped in `@if (weatherPossible())`, so with the
seeded data ONLY the earliest event - the single one inside Open-Meteo's
window - carried a weather module at all, and the other nine event pages had
no module and no explanation. The heading is now always rendered, and
`weatherBlock()` names the case so the panel can say which of the four it is
(past, no coordinates, no readable date, beyond the forecast window) instead
of showing nothing. `canShowForecast()` is still consulted before a request
is attempted - through the same reason, so the two cannot disagree.
WHY A PAST EVENT SHOWS A DISABLED BUTTON
There is nothing left to book, so a link to the registration form would only
lead to a form that refuses to submit. A `<button disabled>` states the
situation ("Registration closed") without inviting the click.

### `clientside/src/app/pages/home/home.ts`

#### class `HomePage`

The home page.
ENDPOINTS USED (three, all read-only)
`GET /api/events/upcoming`  the event grid and the hero's "next events" panel
`GET /api/stats`            the four headline impact figures
(the footer independently calls `GET /api/health`)
WHY `GET /api/organization` IS NOT CALLED HERE
It used to be, for the About section's lead sentence, which read
`organization()?.mission || ('about.mission' | t)`. That made the API's
`mission` field win whenever the request succeeded, so the sentence stayed
English on the Chinese, Vietnamese and Japanese pages - the API's content
layer is English by design (database/02_seed.sql carries the wording), and
the owner has declined a content-localization pipeline. The lead sentence is
the SITE'S OWN copy rather than an organisation's record, so it is the
dictionary's `about.mission` in all four languages now, and the endpoint is
no longer needed on this page at all. `ApiService.getOrganization()` and
`GET /api/organization` are left in place: the API contract, its test and its
documentation still cover the field, and the public site simply no longer
renders it. Removing the call also removed the page's only silent failure -
there is no section left that degrades to English.
HOW THE DATA IS LOADED, AND WHY THIS SHAPE
Each section is loaded separately and fails on its own. That is a deliberate
carry-over from the legacy js/home.js: a failing /api/stats must not blank out
the event listing. The impact figures ARE the "nice to have" of this page, so
they are the ones that degrade to a note; the About section is static copy and
cannot degrade at all.
The event grid is ONE request for the whole visit: `toSignal` over a single
`getUpcomingEvents` call. It used to be driven by `toObservable(sort)` piped
into `switchMap`, because the page carried a sort dropdown of its own; that
control has been removed (browsing is this page's job, sorting is the search
page's), so there is nothing left to re-issue the request and no in-flight
request to cancel - `HOME_LISTING_QUERY` is the only order this page asks for.
`takeUntilDestroyed` still ends the one-off stats request below when the
visitor navigates away.
WHY THE HERO PANEL REUSES THE SAME RESPONSE
"Next events at a glance" shows the first four of the very events already
fetched for the grid. A second request for the same rows would be wasteful and
could disagree with the grid while it is loading.
DESIGN DECISION: no client-side sorting
The listing is fetched with `sort=date&direction=asc`, so the ORDER BY runs
against the whole table rather than only the twelve rows this page asked for,
and the order is a property of the data rather than of this component. A visitor
who wants another order - or any filter at all - uses the search page, which is
where those controls live and which the hero links to.
THE CONTACT DETAILS ARE NOT ON THIS PAGE
The white "Get in touch" section was removed: it repeated the footer's email,
phone, office and hours a couple of hundred pixels above the footer itself. The
footer is now the single home for contact details, and the About card's
"Talk to our events team" button points at `#contact` - the id the footer now
carries - so its fragment still resolves to the contact details instead of to a
section that no longer exists. That button is a plain `href="#contact"` clicked
on this page, so the browser performs the jump itself and the router is not
involved; that was already true of the old `#contact` section, so nothing about
this button changed but its target.
THE ONE FRAGMENT HERE THAT DOES INVOLVE THE ROUTER is `#about`, which the
footer's "About us" link reaches from another route. `withInMemoryScrolling` in
app.config.ts does have `anchorScrolling: 'enabled'`, and it scrolls to the
anchor once, a frame after the route activates - a moment when the event
listing above this section has not been fetched yet, so that first scroll is
against a page that is still short. The second attempt is made by
`shared/fragment-scroll.ts` as soon as this page's own content has arrived,
which is what makes the footer link land here. It is also why this page's two
own fragment links (`#upcoming-events` and `#contact`) need no help: their
targets, the listing section and the footer, are in the document before either
link is clicked.

### `clientside/src/app/pages/not-found/not-found.ts`

The wildcard route's page: a friendly "nothing here" screen.

WHY IT OFFERS TWO ROUTES BACK RATHER THAN ONE
"Home" and "Search" are the two things a visitor who mistyped a URL is most

### `clientside/src/app/pages/search/search.ts`

#### class `SearchPage`

The search page.
ENDPOINTS USED
`GET /api/categories`  the category checkboxes, each with its event count
`GET /api/locations`   the venue picker and the city suggestion list
`GET /api/events`      the search itself, with whichever filters were chosen
THREE DECISIONS WORTH EXPLAINING
1. Client-side validation runs BEFORE the API is called.
A "to" date earlier than the "from" date can never match anything, so
sending it wastes a round trip and produces a confusing "no results" screen
when the real problem is the form. `validate()` returns a message key, the
results panel is replaced by the "please correct the highlighted filter"
state, and no request is issued. The API validates the same rule again - which
is the point: client-side validation improves the experience, server-side
validation protects the data.
2. The filters live in the URL.
After every search the query string is rewritten with `replaceState`, so the
result is shareable and a reload reproduces it. The component also READS the
query string on load and re-runs the search if anything was set, which is
what makes a link like /search?city=Lismore&isFree=true work. Only `from`,
`to`, `city`, `keyword`, `isFree`, `state`, `category`, `sort` and
`direction` are read back - `limit` is an implementation detail.
3. The whole result set is requested in one page.
`limit: 60` rather than the default 20, so a visitor filtering by category
sees everything that matched instead of a first page with no paging control
to reach the rest. The count shown above the grid is the total the API
reports, not just the number of rows received.
4. The page searches on arrival, with a deliberately small first request.
Opening /search issues a real GET /api/events for the default "upcoming"
state with `limit: 9`, so the results column is full the moment the page
renders instead of showing a dashed box that asks the visitor to press a
button before anything appears. Nine rows fill two grid columns without
turning the first paint into a long download; pressing Search events then
runs the same query with the full `limit: 60` documented above. The API's
reported total drives the count either way, so the number shown is the
number that matched and not the number of rows requested - and when the
arrival request came back with fewer rows than matched, the heading drops the
number rather than name a total the grid contradicts. See `resultsHeading`.
5. A native date input paints its own placeholder, and no attribute can change
it.
The two date fields are `<input type="date">`, whose internal
`yyyy/mm/日`-style placeholder is drawn by the browser in the BROWSER's own
locale and not the document's. Measured with puppeteer against the running
build in the Edge used for testing: launched with `--lang=zh-CN` the empty
field paints `yyyy/mm/日` even when the input carries `lang="en-AU"` and
`<html lang="en-AU">`; launched with `--lang=en-US` the very same markup
paints `mm/dd/yyyy`. Removing the `lang` attribute, or moving it to the
fieldset or to `<html>`, changed nothing. So the page cannot make the
control display `yyyy-mm-dd`, and the hard-coded "Format: yyyy-mm-dd" line
that used to sit above each field was removed rather than left to contradict
the control - the `search.dateHint` line beneath still shows a valid
example, which is true in every locale. The submitted value format IS
guaranteed by the spec (`yyyy-mm-dd`, checked by `validate()` below), and
that is the part the page is responsible for.
THAT REMOVAL WAS COMPLETE, which a later review of the gap between the two
date fields required proving rather than assuming: the rendered page holds
zero `.field__format` elements and no stylesheet matches the class, so no
wrapper, margin or reserved height survived it. The 69.59px the review
measured between "From date" and "To date" was the empty `.field-message`
slot under the first field (41.6px of it) plus that field's own bottom
margin and the row's gap. Both are fixed in styles.css - see THE FORM RHYTHM
there - and the message slots now bind their text with `[textContent]` so
`.field-message:empty` can collapse them.
6. The filter panel filters as the visitor changes it, and it says so.
Every control in the panel applies itself: a tick, a radio, a picked
suggestion in the venue combobox or the sort order runs the search at once, and
the two date fields and the keyword box run it 350ms after the last keystroke
(`runSearchSoon`) so a word is searched once rather than once per letter. The
rule is stated in the panel's action row through `search.resultsHint`, in all
four languages.
THE VENUE COMBOBOX IS THE ONE CONTROL WITH TWO GESTURES, and it treats them
differently on purpose: TYPING filters its own suggestion list and asks the API
for nothing, because the value this field sends is a chosen town or venue and a
half-typed word is not a filter the visitor has chosen; PICKING a suggestion is
the commit and applies at once, exactly as the `<select>`'s `change` did. So the
"filters as you change it" rule still holds for every change of the FILTER, and
no other control on the page changed its timing.
WHY THIS RATHER THAN AN EXPLICIT SUBMIT WITH A PINNED ACTION ROW - which is
the other model the review offered - is a measured decision, not a preference.
The pinned row was built first: `position: sticky; bottom: 0` on the action
row, with the model sentence inside it. Sweeping every scroll position at 60px
steps and measuring the overlap between the pinned row's box and every control
in the panel, the worst case was 100% - the bar FULLY covered `category-7` at
1440x900 and the venue field at 390x844, on first paint, which is exactly the
"it floated over the form it belongs to and covered the City field on first
paint" the previous round recorded against pinning this row. A row pinned to
the viewport bottom overlays whatever the panel has at that height, at every
scroll offset, and no amount of trimming its height fixes that. So the panel
applies itself instead, nothing floats, and the page still scrolls once.
THE SUBMIT BUTTON STAYS, as the explicit "search now" control at the end of the
panel: pressing it re-runs the query the live model has already applied, which
is idempotent for a GET, and the end-to-end suite finds it by its text
(tests/angular-e2e.mjs, read-only). Before this round the panel was a mixture -
the category boxes, the chips and the sort dropdown re-ran the search as they
changed while the dates, the venue, the keyword, the free-events box and the
event-state radios waited for the button - which is what made the model
unanswerable from the outside. The sort dropdown and a chip's remove button act
on the result set already on screen and behave exactly as they did; the chips
describe the applied set rather than the form (see `applied`), so a search still
in its debounce window cannot leave the chips describing results they did not
produce.
The category and venue lists are loaded with `forkJoin` so both requests are in
flight at the same time; each half also has its own `catchError`, so a failed
category lookup still leaves a usable city and date search rather than an empty
page.

### `clientside/src/app/shared/api-status.ts`

#### class `ApiStatusComponent`

The live API status indicator in the site footer.
It reports three states rather than two, and a failure is informational rather
than an error message.
Endpoint: `GET /api/health` (ApiService.getHealth()).
WHY IT LIVES IN ITS OWN COMPONENT
The footer is rendered on every route, so this is a request that runs on
every page. Keeping it separate means the footer template stays static and
this is the only thing that changes once the response arrives.
WHY THE THREE STATES RATHER THAN TWO
The legacy footer distinguished `database.connected === false` ("the API is
up but the database is not") from a failed request ("the API is offline").
Those are different problems with different fixes, and collapsing them into
one red label would hide the more confusing case - an API that answers with
valid JSON but cannot read any events. `database.connected` is `null` when
the local data source is in use, which is why the test is `!== false` rather
than `=== true`.
WHY A FAILURE IS NOT AN ERROR MESSAGE
The status line is informational. A visitor does not need a red error panel
because a health check failed; the pages themselves already report their own
loading failures in context.
The request is issued ONCE, from the constructor, and `takeUntilDestroyed` ends it
with the component - see the note on the constructor for why that lifetime is the
point rather than a formality.

### `clientside/src/app/shared/event-card.ts`

#### class `EventCardComponent`

One event card, shared by the home page's "upcoming events" grid and the search
page's results.
This is a direct port of the legacy `eventCard()` in js/dom.js, which both pages
called too - the markup, the class names and therefore the styling are
identical to the pre-Angular site.
WHAT THE CARD SHOWS, AND WHY
* artwork, with the derived state badge ("Past event" / "On now") overlaid WHEN
THE EVENT IS NOT UPCOMING, so a state that differs from the ordinary one is
visible before anything is read
* category chip and a price pill
* title, carrying the card's ONE link to the event's own page - a link that
covers the whole card, so the artwork and the empty space around the text
are part of the same target (see WHY THE WHOLE CARD IS ONE LINK NOW)
* short description
* a three-row list of When / Where / Cause - the three questions a visitor

* the compact fundraising bar
* a "View details" affordance, drawn with the button's own appearance and read
as decoration: the card is already the control it appears to be

This card is shared, so the rule lives in the card and not behind a per-page
flag: one page must never be able to disagree with the other about what the
same event is. The home page lists upcoming events only, so an "Upcoming" badge
there sat directly above the brown category chip and told the visitor nothing
the listing had not already told them - two pills competing for the same glance.
The information that actually differs is "this one has finished" or "this one is

kept here because the trade-off it named is still real: "only the artwork and

nested anchors, which is invalid HTML, and it would also stop a visitor from
selecting the summary text." The review asked for the whole card to be a
target, so the three anchors became ONE - the title's, stretched over the card

note named is accepted and is now the card's documented behaviour: the overlay
sits above the summary, so selecting that text by dragging takes a modifier
key. Nothing else about the card changed: the artwork is still a described
<img>, the button is still drawn with its visible words, and every link still
carries an accessible name that names the event.

Registering is per event, so it starts from the event's own page where the
event is unambiguous. A Register button on every card would also mean twelve
destinations with identical accessible names in one list.

### `clientside/src/app/shared/fragment-scroll.ts`

#### class `FragmentScrollService`

- `@file Makes a cross-route fragment link land once the page under it exists.`
THE DEFECT THIS EXISTS FOR
A `routerLink="/"` carrying `fragment="about"` navigates correctly - the URL
lands on `/#about` - but the router scrolls to the anchor about a frame after
`NavigationEnd`, while the home page's event listing is still being fetched,
so that scroll is made against a page that is still SHORT: the anchor is where
the About section is at that instant, not where it ends up. Measured in
headless Edge at 1400x1000 with `GET /api/events/upcoming` delayed 600ms:
`BrowserViewportScroller.scrollToAnchor` asked for top 1274.95 - the section's
position at that moment, 1px inside the page's whole scroll range of 1276 -
and the section finished at document y 2469.5 once the twelve event cards had
rendered, leaving the visitor 1149px short of the section the link named.
Touching the wheel before the listing arrives makes that short landing
permanent (measured 1226.5px short, and still short a second later), which is
the 1183px shortfall the review recorded at 1440x1080 - scrollY 1287 against
the section's y 2470 - and the reason a previous round removed the footer link
rather than shipping it.
WHY THE PAGE HAS TO MAKE THE SECOND ATTEMPT ITSELF
The router's `anchorScrolling` (`withInMemoryScrolling` in app.config.ts) is
one attempt, made when the route activates, and there is nothing in the router
for it to wait on. Chromium does keep a "fragment anchor" alive after a
fragment navigation and re-scrolls to the element as the document grows, which
hides the defect while the visitor touches nothing - measured: the same click
with no input ends at scrollY 2470 with no code of ours involved. That is a
browser heuristic rather than a contract: the first scroll gesture releases it,
and a visitor who so much as nudges the wheel is left where the short page
stopped. Measured again for this round on the same click, with this service's
per-frame pass suppressed and a wheel gesture 150ms after the click: the
section came to rest 119.5px below the top of the viewport - the short page's
position plus one wheel notch - and stayed there. So the second attempt is
made here, from the page that knows when its own content has arrived.
WHAT IT DOES, AND WHAT STOPS IT
After a navigation that names a fragment, one frame in every animation frame
asks whether the fragment has actually landed: the element is measured against
its own resting line - the top of the viewport, or its `position: sticky` `top`
for an element the stylesheet holds there - and scrolled to exactly the way the
router scrolls to it (`rect.top + scrollY`, the element's top at the top of the
viewport) when it is more than
{@link LANDING_TOLERANCE_PX} below that line AND layout is still arriving -
either the document grew on this frame, or it grew within the last
{@link QUIET_MS_BEFORE_A_GESTURE_WINS} milliseconds. A landed fragment is
therefore left alone, which is every same-route fragment click on a finished
page: the router's single attempt is already correct there and this service
never touches the scroll. The watch also stops on a new navigation (a URL
without a fragment cancels it outright), at the end of
{@link SETTLE_WINDOW_MS}, and when the component that owns it is destroyed.
The second half of that condition is what ends the watch early. A fragment at
its resting line on a page that has gone quiet has nothing left to land, so the
watch stops there rather than sampling every frame for the rest of the four
seconds - measured: after the "Get tickets" click it runs for the length of the
quiet window instead of two hundred and forty frames, and a deep link that is
already correct when it arrives stops in the same way.
WHY A SCROLL GESTURE WINS, AND WHAT COUNTS AS ONE
"Below the resting line" is not on its own a reason to scroll: the visitor can
put the element there deliberately, and the condition above cannot see the
difference between that and a layout that has not settled. The first version of
this service could not either, and that was a regression a visitor hit at once.
On `/events/2`, `#tickets` is `position: sticky` (`.panel--sticky`): at rest its
top is its sticky line and this watch is satisfied, but the moment the visitor
scrolls UP the card un-pins and its viewport top falls below that line, so the
watch read the gesture as "the fragment has not landed" and requested the old
position again - three times, on three frames, inside the four-second window.
Measured at 1400x1000 after clicking the hero's "Get tickets": the wheel moved
the page 1331 -> 1211, and the watch put it back to 1331.21875 on each of the
next three frames (1549ms, 1648.9ms and 1715.7ms), all three with the stack
`FragmentScrollService.scrollTo -> settle`. Scrolling down was unaffected - a
downward wheel leaves the card pinned at its line, which the old test already
answered "landed" - so the page felt frozen in exactly one direction for the
two and a half seconds of window that were left.
What separates the two cases is what happened to the DOCUMENT, not what
happened to the viewport: a gesture - a wheel, a scrollbar drag, an arrow key -
moves the viewport and leaves `documentElement.scrollHeight` exactly where it
was, while the home page's listing arriving above `#about` makes it 1195px
taller. So the watch scrolls only while the document is still gaining layout,
and once it has held its height for
{@link QUIET_MS_BEFORE_A_GESTURE_WINS} it concludes that what moved the
fragment was the visitor and stands down. That is the whole of "a deliberate
scroll gesture always wins"; no `wheel`/`touch` listener is involved, so there
is no input to miss, and the cross-route case is untouched because it is the
page growing, not the visitor, in the frames that land it.
THE QUIET IS A LENGTH RATHER THAN A FRAME, and that is the one judgement in
here that could have been made the other way. A single frame of "the page did
not grow" is enough to prove that frame was not a render pass, but it is not
enough to prove the page has finished: the listing is rendered in one piece,
and the frame after it is quiet. It is the event page that shows the difference
- measured there, the document was still growing from 2755px to 3053px inside
the window that starts when the hero link is clicked - so the watch waits out a
short quiet before it lets a gesture decide, and the cost is that a gesture made
on a page that is still assembling can be undone once, after which the watch
stands down and leaves the visitor where they are.
WHY THE DOCUMENT'S HEIGHT RATHER THAN THE ELEMENT'S OWN POSITION. The obvious
measurement - "has the fragment moved further down the document?" - cannot work
for the element this had to be fixed for, and the numbers say so plainly.
Measured on `#tickets` at 1400x1000: with the card unpinned at scrollY 1331 its
`rect.top + scrollY` reads 1331, and once the card is pinned by exactly that
scroll it reads 1427.31 - the pixel expression the router itself uses moves
96.31px when the STYLESHEET moves the card, so a watch comparing it against its
own last landing would see growth on every frame after a successful sticky
landing and scroll for the rest of the window. The document's height has no
such state: it changes only when the page gains or loses layout.
WHY IT CANNOT LOOP
Each pass ends when the fragment is at its resting line, and a page that has
gone quiet is not scrolled at all - the condition for scrolling requires layout
to have arrived, so a still page is never moved twice. The one page where the
line cannot be reached - a fragment on the LAST element, the footer's
`#contact`, which no scroll can bring to the top of the viewport - is left alone
as soon as the page is scrolled as far as it goes, so the browser's own clamp is
not re-issued every frame.
WHY A NAVIGATION FROM THE BROWSER'S HISTORY IS LEFT ALONE
The router restores a Back/Forward position itself, and scrolling to an anchor
the visitor has just navigated away from would fight it: the `popstate` trigger
is therefore skipped, so history restoration behaves exactly as it did before
this service existed.

### `clientside/src/app/shared/page-title.ts`

#### interface `DocumentTitle`

Set the browser tab title from a route's `data.titleKey`, in the active
language.
- `@file The shared public-site page-title helper.`
WHY NOT THE ROUTE'S OWN `title:` STRING
The router evaluates `title:` once, without the TranslationService, so a site
that offers four languages would keep an English tab title after the visitor
switched to Chinese or Vietnamese. Instead every route carries a translation
KEY in `data.titleKey` and each page calls this once:
readonly title = useDocumentTitle();      // field initialiser
constructor() { this.title.set(); }       // from data.titleKey
...
next: (event) => this.title.set('event.detailTitle', { name: event.eventName })
An impure `TranslatePipe` cannot help here, because document.title is not part
of any template.
WHY THIS IS A FACTORY THAT CAPTURES AN INJECTOR RATHER THAN A PLAIN FUNCTION
`inject()` only works inside an injection context - a field initialiser, a
constructor body or a factory. A page has to set its title at least twice: once
when it is created (from the route data) and once when the API answers, from
inside an RxJS `next` callback, which is NOT an injection context. A plain
function calling `inject()` therefore works the first time and throws NG0203
the second.
`useDocumentTitle()` is called from a component field initialiser - a real
injection context - so the Injector it captures is that COMPONENT's injector.
`runInInjectionContext` then re-enters it for every later call, which means
`inject(ActivatedRoute)` resolves to the route the component belongs to rather
than to nothing. That is the whole reason the injector is captured instead of
the three services: resolving ActivatedRoute eagerly at module scope would look
for it in the root injector, where it does not exist.
`snapshot` is used rather than the `data` observable because a page sets its
title once per state; when the route changes the router destroys and recreates
the component, and a fresh instance calls this again.

#### function `useDocumentTitle`

Create a title setter bound to the calling component's injector.
- `@returns The setter the calling page calls from its constructor and again`
whenever the page's own title changes.

#### interface `ApiErrorDetail`

The payload a failed write returns.
Two DIFFERENT shapes travel in `details`, which is why almost every field here
is optional:
a 400 (validation)  an ARRAY of { field, message } - one entry per problem,
rendered next to the offending form control
a 409 (conflict)    an OBJECT of facts about the clash, with no `message`
field of its own:
{ eventId, eventName, registrationCount, suggestion }
The 409 is the delete rule: the event cannot be removed because registrations
exist, so the API puts the numbers the UI needs to explain itself in that
object. The ENVELOPE still carries a sentence about the clash (the live body
reads `"X cannot be deleted because 4 registrations have already been recorded
for it..."`), but the object does not, and that distinction is what the
paragraph below turns on. `message` on a detail is therefore optional, and an
accessor that insists on it will silently return nothing for every conflict -
which is exactly the bug ApiError.conflictDetails used to have.

### `shared/src/util/format.ts`

#### function `formatCurrency`

Format a fundraising total as whole Australian dollars.
- `@param amount - A number, or a numeric string straight from the API, or null when the`
API sent no figure, which is treated as zero rather than rendering as "NaN".
- `@returns The amount as currency, for example 25000 becomes "$25,000".`

#### function `formatPrice`

Format a ticket price with its cents.
Cents are shown here but not on a fundraising total, because a price is money
a visitor actually pays and "$45" next to "$45.50" would look like a mistake.
- `@param amount - A number, or a numeric string straight from the API, or null when the`
API sent no figure, which is treated as zero.
- `@returns The amount as currency, for example 45 becomes "$45.00".`

#### function `formatDate`

Format a stored date in full, in the assessed Australian locale.
- `@param isoDate - A `YYYY-MM-DD` date as the database stores it.`
- `@returns The date written out, for example '2026-10-11' becomes 'Sunday 11 October`
2026'; an empty string when `isoDate` is missing, and the input unchanged when it
cannot be parsed - including a day that does not exist, such as '2026-02-30' -
so a bad value is visible rather than silently replaced.

#### function `formatShortDate`

Format a stored date in the short form a card or a list row has room for.
- `@param isoDate - A `YYYY-MM-DD` date as the database stores it.`
- `@returns The abbreviated date, for example '2026-10-11' becomes '11 Oct 2026'; an`
empty string when `isoDate` is missing, and the input unchanged when it cannot be
parsed, including a day that does not exist such as '2026-02-30'.

#### function `formatTime`

Format a stored clock time as a visitor reads it.
The time is placed on today's date purely to borrow `toLocaleTimeString`; only
the time part is ever returned.
The parts are CHECKED, not handed straight to `Date.setHours`. That call does
not reject nonsense: it rolls it over, so '99:99' used to render as "4:39 am",
'24:00:00' as "12:00 am" and '-1:30' as "11:30 pm" - a plausible-looking time
invented from a bad value - and a non-numeric value ('abc') produced the
literal string "invalid date", which is English in all four languages. Anything
that is not a real clock time is therefore returned unchanged, the same way
formatDate and formatDateTime already report a value they cannot read.
- `@param time - A `HH:MM:SS` time as the database stores it. `HH:MM` is accepted too.`
- `@returns The time in lower case 12-hour form, for example '07:30:00' becomes`
'7:30 am'; an empty string when `time` is missing, and the input unchanged when it
is not a clock time.

#### function `maskAttendeeName`

Mask an attendee's name as "Grace T." for a public list.
WHY THE PUBLIC PAGE MASKS AT ALL
The event detail page lists who has registered, which is the feature the
brief asks for, and that list is visible to anyone. A full name beside a
ticket count and a purchase date is enough to identify and contact a person,
so the page shows a first name and the initial of the surname: enough for the
visitor who booked to recognise their own row ("yes, that is mine"), and not
enough to publish somebody else's identity. The API does the same thing at the
query, and this helper is the client-side fallback for a response that carries
only the full name.
A single-word name is returned as it is, because "Grace" has no surname
initial to take and inventing one would be wrong. An empty name yields an
empty string so the caller can fall back to the registration id.
- `@param attendeeName - The name as stored, in any casing, or null when the row carries none.`
- `@returns The masked name, for example 'Grace T.', or an empty string when there is no name.`

#### function `backerName`

The backer name under a registrations row: who, in the short form the API sends.
The ticket count and the purchase date have their own columns in that table, so only
the name is rendered.
Built from the masked name the API sends (`attendeeDisplayName`) where it is
present, and from the full name via maskAttendeeName() otherwise, so the same
mask is produced whichever shape arrived. The ticket and date halves are added
by the component, because they are dictionary text and belong to the active
language rather than to this function.
- `@param registration - The registration row, public or admin shape.`
- `@returns The masked backer name, or an empty string when the row carries no name.`

#### function `formatDateRange`

Format an event's dates, including multi-day events.
A single-day event shows one date; the three-week art exhibition shows a range.
The fallbacks are `||`, not `??`, and that is deliberate: this is a port of the
vanilla formatDateRange(), and an EMPTY `dateStart` is "no start recorded"
rather than a value. With `??`, `{ dateStart: '', eventDate: '2026-10-11' }`
returned '' - an event with a perfectly good eventDate rendered no date at all.
- `@param event - The event whose dates are wanted.`
- `@returns The short date, or the short start and end dates joined by a hyphen, or an`
empty string when the event carries no usable date at all.

#### function `formatTimeRange`

Format an event's start and end times as one range.
- `@param event - The event whose times are wanted.`
- `@returns The two times joined by a hyphen, the start time alone when no end time is`
recorded, or an empty string when the start time is missing.

#### function `formatDateTime`

Format a registration timestamp as a date and a time.
- `@param value - A `YYYY-MM-DD HH:MM:SS` timestamp as the API sends it.`
- `@returns The timestamp such as '14 Sep 2026, 8:57 am', an empty string when `value``
is missing, and the input unchanged when it cannot be parsed.

#### function `stateKey`

The translation key for a derived event state.
Returns a KEY rather than translated text so the caller can render it with the
active language and have the label update when the language changes.
- `@param eventState - The state the API derived from the event's dates, or null when the`
endpoint did not send one.
- `@returns The i18n key for that state, and 'state.event' for a missing or unrecognised`
value so a label always renders.

#### function `imageUrl`

The image URL for an event.
A bare filename ("gala-dinner.svg") is resolved against the shared assets
folder; an absolute URL (an administrator pasted a real photo URL) is used
unchanged. An event with no image gets the same fallback artwork as before.
- `@param event - The event whose artwork is wanted. May be null or undefined, in which`
case the fallback artwork is returned.
- `@returns A URL a template can bind to directly: the stored filename made absolute, an`
external or data URL left as it is, or the project's fallback image.

#### function `capacityLabel`

How full an event is, as one short label.
- `@param event - The event whose capacity is wanted.`
- `@returns A label such as "12 / 200", or an empty string when the event records no`
capacity, because "12 / null" would be worse than showing nothing.

### `shared/src/weather/weather.service.ts`

#### type `ForecastUnavailableReason`

Why an event cannot have a forecast, for a panel that has to say so.
The four cases are the honest answers to "why is there no forecast here?", and
the event page renders one translated sentence per case. They are a union
rather than free text so the reason cannot drift into an English sentence
inside the shared library, where no dictionary could translate it.
noCoordinates   the venue publishes no latitude/longitude ("Online")
noDate          the event carries no readable YYYY-MM-DD date, or no target
was handed over at all
past            the day has gone; what the weather WAS helps nobody
beyondHorizon   the day is further ahead than the daily forecast reaches

#### class `WeatherService`

Fetch the daily forecast for an event, from the browser.
The forecast is a bonus, so this service is deliberately quiet: every failure
resolves to null instead of rejecting, and the caller renders the panel
unconditionally. The coordinates come from the event itself, which the API
serves from `locations.latitude` / `locations.longitude`.
