# Settings: dark theme and language

This document describes the two settings controls added to the client, how they
are implemented, and - importantly - what they deliberately do **not** do.

---

## 1. What was added

| Control | Where | Values | Remembered |
| --- | --- | --- | --- |
| Theme switch (button) | Header, next to the menu | Light, Dark, System | `localStorage` key `charity-events:theme` |
| Language picker (`<select>`) | Header, next to the theme switch | English, 中文, Tiếng Việt, 日本語 | `localStorage` key `charity-events:language` |

Both controls are generated by `clientside/js/nav.js`, so they appear on the
home page, the search page and the event detail page.

### The theme switch

A single button cycles **light → dark → system** and shows the current setting
("Theme: Dark"), so it doubles as a status indicator. Three states rather than
two because "follow my computer" is what most visitors expect by default, and
it keeps following the system if the visitor changes it while the page is open.

### The language picker

A native `<select>`, chosen because it is keyboard accessible and behaves
correctly on phones without extra code. The label of each option is written in
its own language (中文, Tiếng Việt, 日本語), which is the convention for language
pickers: a visitor who cannot read the current interface language can still
recognise their own.

---

## 2. Important scope limit

**Only the interface is translated. Event content is not.**

Event names, descriptions, venue names and organisation names come from the
MySQL database in English (`Riverside Rainbow Fun Run 2026`,
`Lismore Riverside Park`, and so on). Translating that content would need either
translated columns on every content table or a separate translations table keyed
by language - a content management feature well beyond Assessment 2.

Rather than leave the visitor guessing, the header shows a short note while a
language other than English is selected:

> Interface language only; event details stay in English.

(The note is itself translated, and is hidden in English.)

## 3. Files

| File | Responsibility |
| --- | --- |
| `js/translations.js` | All four dictionaries, 323 keys each, plus the `translate()` helper |
| `js/i18n.js` | Reads and stores the choice, walks the DOM applying translations |
| `js/theme.js` | Reads and stores the theme, resolves "system", writes `data-theme` |
| `js/nav.js` | Builds both controls; rebuilds the header and footer on a language change |
| `css/styles.css` | The `[data-theme='dark']` token overrides and component fixes |
| `tools/check-translations.mjs` | Fails if the four dictionaries differ, or if markup references a missing key |
| `tools/sync-theme-snippet.mjs` | Keeps the inline theme script in step with `js/theme.js`, across every page it discovers (nine of them since A3) |
| `tools/check-contrast.mjs` | Measures the contrast of every text element in both themes |

## 4. How the markup is translated

English stays in the HTML on purpose: the page is readable before the script
runs, and it is the fallback whenever a key is missing.

```html
<!-- element text -->
<h1 data-i18n="home.title">Every ticket you buy becomes help someone can feel.</h1>

<!-- an attribute, possibly several -->
<input data-i18n-attr="placeholder:search.cityPlaceholder"
       placeholder="Start typing, e.g. Lis" />
```

Text that the page controllers generate (event cards, filter chips, the progress
bar, validation messages, the modal) goes through the same helper:

```js
import { t } from './i18n.js';
el('span', { text: t('event.raisedSoFar') });
```

Placeholders use braces and are substituted without touching the DOM:

```js
t('search.eventCountMany', { count: 12 })   // "12 events matched your filters."
```

## 5. Avoiding a white flash

The stored theme can only be read once JavaScript runs. If that happened after
the stylesheet was applied, a visitor who chose dark would see a white flash on
every page load. Each page therefore carries a tiny inline script in its
`<head>`, **before** the stylesheet link:

```html
<!-- theme-boot -->
<script>(function(){try{var p=localStorage.getItem('charity-events:theme')||'system'; ... })();</script>
<!-- /theme-boot -->
```

That snippet duplicates the storage key and attribute name used by `js/theme.js`,
so it is **generated** rather than hand-written:

```bash
node tools/sync-theme-snippet.mjs          # write it into every page that has the markers
node tools/sync-theme-snippet.mjs --check  # fail if a page is out of date
```

The tool walks `clientside/` and finds the pages itself rather than using a
hardcoded list, because A3 took the site from three pages to nine (four public,
five admin). A list would have meant six pages quietly had no theme boot, and the
only visible symptom would be a white flash for a dark-theme visitor - which
nobody notices while marking.

## 6. How the dark theme is built

Every colour in the light theme is already a custom property, so the dark theme
is one block of token overrides:

```css
[data-theme='dark'] {
  --surface-0: #16211f;
  --ink-900: #eef4f3;
  --line: #2c3a38;
  /* ... */
}
```

A handful of components were not driven by tokens alone and are fixed
explicitly: the header's translucent background, the hero gradient, the white
form controls (including inverting the calendar icon inside a date field), cards
and panels, the modal backdrop, and the event artwork, which is dimmed slightly
so it does not glare against a dark card.

## 7. Testing

### Automated

```bash
node tests/run-tests.js            # 64 checks, including six for the settings
node tools/check-translations.mjs  # dictionary completeness
node tools/sync-theme-snippet.mjs --check
node tools/check-contrast.mjs      # contrast in both themes
```

The six settings checks cover: four language options are offered and a switch
translates the page and updates `<html lang>`; a remembered language is applied
on the next page; all four dictionaries have identical keys; the theme cycles
light → dark → system and is stored; the dark theme is a set of token overrides
plus the component fixes; and every page applies the theme before the
stylesheet.

### Manually

Open the site and use the two controls in the header. The theme defaults to
following the operating system, so setting Windows to a dark app mode is enough
to see the dark theme without touching the switch. Language can also be forced
with a query string, which is handy for a screenshot or a demonstration:

```
http://localhost:5500/index.html?lang=ja
```

`?lang=` accepts `en`, `zh`, `vi` and `ja`, and takes precedence over the stored
choice for that page load.

## 8. Assessment note

The A2 brief asked for three pages (Home, Search, Details), a menu on every page,
basic DOM manipulation and "Goal vs. Progress". A3 adds the registration page and
a separate admin site, and the theme and language features remain **not** required
by either brief; they are additional work. Three consequences worth being clear
about:

1. **The admin site is deliberately English-only.** It keeps its own strings in
   `admin/js/admin-i18n.js` rather than loading the four-language dictionary,
   because localisation is a feature of the *public* site and the A3 brief asks
   the admin site for event management. Its call sites go through the same
   `t(key, values)` shape, so translating it later would touch one file.

1. **You must be able to explain every line**, including why `matchMedia` is
   used, why the theme is applied before the stylesheet, and what
   `data-i18n-attr` does. The remarks in each file are written to make that
   possible.
2. **The translations are machine-written.** Chinese, Vietnamese and Japanese
   interface text was produced by an AI assistant, not a native speaker. If the
   phrasing matters to you, have a native speaker review
   `js/translations.js` - it is a flat list of key/value pairs, so corrections
   are a one-line change each. `node tools/check-translations.mjs` will confirm
   nothing was lost in the process.
