Storyboard — 9 screens

PROG2002 A3 - Charity Events Website. One screen per page of the two Angular applications. Every line below is taken from the delivered components and their templates, the shared TypeScript library and the API, not written from memory.

HOME-01 — Home page

TITLE: Home page SCREEN ID: HOME-01 DATE: 15/10/2026

clientside/src/app/pages/home/home.ts + home.html · route /

① ELEMENTS:
ELEMENTS:
  • Application chrome, shared by both websites: layout/site-header.ts with the brand, the settings-bar (language picker and theme button) and the menu (Home / Search events / Admin site), and layout/site-footer.ts
  • Hero: h1, lead paragraph and two call-to-action links, one of them a router link to /search
  • "Next events" aside (hero__panel) listing the next few events, each a router link to /events/:id
  • Statistics band with a tile per figure
  • Events section: a count, a sort <select id="home-sort"> and a grid of <app-event-card> components
  • Error state and empty state for the listing
  • About section with two sub-headings, and a contact section with the organisation name
GRAPHICS:
  • Hero is a full-width dark brand panel drawn with a CSS gradient; no image file is loaded for it
  • Each event card carries a 16:9 illustration chosen from the nine committed SVGs, resolved from APP_CONFIG.imageBaseUrl plus the event's stored imageUrl
  • The goal bar is the shared progress-bar component, so the bar and the numbers beside it are computed from one value
  • Statistics sit in a responsive grid; the number is large and the label is small
  • The event grid is CSS Grid with auto-fit columns; one column on narrow screens
  • Icons are inline SVG or text glyphs; no icon font is loaded
TEXT:
  • h1 and lead from the client dictionary, as every other string on the page is
  • Section headings: the hero panel, the statistics band, the events section, About, and the contact details in the footer
  • Two call-to-action labels in the hero, and the aside heading
  • No sort control on this page: sorting and filtering belong to the search page, which the hero links to
  • State badges on each card: upcoming, ongoing or past
AUDIO/VIDEO:
  • No audio and no video element on this page.
  • The moving parts are states rather than media: the panels show a loading line until the API answers, the sort re-renders the grid, and the language and theme switches repaint the page in place.
NOTES
  • The page is one standalone Angular component in a zoneless application: the template's @if and @for blocks render from the component's signals, so there is no manual DOM update anywhere on the page.
  • Three requests feed it - the upcoming events, the statistics and the featured organisation - and all three go through shared/src/api/api.service.ts. No component calls fetch and no component builds a URL.
  • The list itself is not sorted in the browser. The component holds the events in a signal and renders whatever order the data is in; the sort control changes that order in the component, which is why there is only one place that decides it.
  • The language picker marks the selected <option> itself with [selected] as well as binding the select's value. A value written before a loop has created its options is discarded, and the browser then shows the first option - which is how a Chinese interface once displayed a picker reading "English". The same fix is in the registration page's ticket-tier picker and in the search page's venue picker.
  • The theme is applied before the application loads by a small inline script in index.html, so a dark-theme visitor does not get a white flash on every navigation.
Description:

Public landing page. Static welcome copy at the top, live panels below it, and one shared card component rendering every event.

Content:
  • Next-events aside <- GET /api/events/upcoming
  • Statistics tiles <- GET /api/stats
  • Event cards <- GET /api/events/upcoming
  • Organisation block <- GET /api/organization
  • Each card shows: illustration, state badge, category, name, short description, date, venue, price from, and goal progress
  • Only current and upcoming events appear here, because the upcoming endpoint is defined that way
Interactions:
  • Click a card or its link -> /events/:id
  • The event grid is not re-sortable here by design: the hero links to the search page for that
  • Change language -> every labelled string switches and the choice is stored in localStorage under one key shared by both applications
  • Change theme -> light, dark or follow system, persisted and applied before paint
  • The page cannot hang: every API call carries a ten-second timeout and every failure becomes one ApiError, so there is a single error shape to render
Media Creation:
  • Illustrations: nine hand-authored SVG files, one per category, listed once in shared/src/config/app-config.ts so the public pages and the admin form cannot disagree about which artwork exists
  • No stock photography and no external image host, so nothing can 404 at marking time
  • Card markup exists once, in shared/event-card.ts and event-card.html; the home page and the search page both render that component
Navigation:
  • Entry points: the site root, the brand link, or any menu item
  • Leaves to: /search, /events/:id, the admin site through the cross-site link, and the in-page sections
  • The menu deliberately has no "Register" item: registration is per event, so it starts from an event page

TITLE: Search events SCREEN ID: SEARCH-01 DATE: 15/10/2026

clientside/src/app/pages/search/search.ts + search.html · route /search

① ELEMENTS:

GRAPHICS:
  • Filter panel is a bordered card; each group is a fieldset with its own legend
  • Category checkboxes sit in a responsive auto-fit grid
  • Results use the same event-card component as the home page, so a card looks the same everywhere
  • Each active filter is a chip with a remove control, whose accessible name says which filter it removes
  • Error messages sit directly under the field they belong to
TEXT:
  • h1: the search page title from the client dictionary
  • Filter heading with the hint that every criterion is optional
  • Five fieldset legends: When, Where, What kind of event, Other options, Event state
  • Labels: from date, to date, venue, category group, free events only, include finished events
  • Hints: the date format, and what leaving a field blank means
  • Results heading, count line, active-filter label, and the idle and no-results headings
AUDIO/VIDEO:
  • No audio and no video.
  • The count line, the results grid and every field message are live regions, so a search that changes the results is announced rather than silently swapped.
  • Nothing autoplays and no media is embedded.
NOTES
  • Every criterion is optional and they combine on the server, not in the browser, so the same URL can be replayed and shared.
  • The filters are written into the address bar and read back on load. The venue is restored into the picker as well as into the query, because the picker's options carry [selected]: a value written before a loop has created its options is discarded, and the page used to filter by a venue while showing no venue selected.
  • The whole filter form is one value held in a signal, so Clear is a single write and every control follows; there is no loop over the DOM.
  • The component does not build a URL either. It produces the API's query parameters and hands them to ApiService, which owns the base URL, the timeout and the error shape.
  • The search is one request. The count in the results heading comes from the response's meta block, not from a second call.
Description:

Filter page. Optional criteria, all applied as query parameters on one API call, with the state kept in the URL.

Content:
  • Category checkboxes <- GET /api/categories (name plus active event count)
  • Venue list <- GET /api/locations (venues that host at least one active event)
  • Results <- GET /api/events with from, to, venue, category, state, free-only and sort parameters
  • Count line <- the meta block of the same response
Interactions:
  • Submit the form -> one API call, the grid is replaced and the URL is updated
  • Remove a chip -> that one criterion is cleared and the search runs again
  • Clear -> all criteria are cleared, the URL is cleaned and the full list is returned
  • Click a result -> /events/:id
  • Open a shared filtered URL -> the same view is restored, including the venue picker
Media Creation:
  • No new artwork: the page reuses the event card component and the nine category SVGs
  • The numbering and legends are text, not images, so they translate with the rest of the page
Navigation:
  • Entry points: the menu, the home page's hero button, or a shared filtered URL
  • Leaves to: /events/:id for any result, and / through the breadcrumb
  • Returning to this page with filters still in the URL restores the same view

One event in full: the story, the numbers, the ticket tiers, the registrations so far, and the way in to registration.

Content:

Media Creation:

Navigation:
  • Entry points: any event card on the home page or the search results
  • Leaves to: /register/:id, /search, or / through the breadcrumb
  • This is the only route into registration, by design

REGISTER-01 — Event registration

TITLE: Event registration SCREEN ID: REGISTER-01 DATE: 15/10/2026

clientside/src/app/pages/register/register.ts + register.html · route /register/:id

① ELEMENTS:
ELEMENTS:
  • Breadcrumb: Home / Search events / this event / Register for an event
  • Event summary panel: the event being registered for, with its date and venue, so the visitor can see what they are registering for before typing anything
  • h1 and a lead line
  • Form group "your details": name, email, optional phone, and a notes field
  • Form group "booking": ticket tier and number of tickets
  • A running total computed from the chosen tier and the quantity
  • Per-field error messages and a summary that is announced and takes focus
  • Submit button with a busy state, and a cancel link back to the event
  • Success panel built from the API response, listing what was booked
  • A "no event chosen" state, and an error state if the event cannot be loaded
GRAPHICS:
  • The form is a single-column card, so the reading line stays short
  • Required fields are marked with an asterisk in the label, not with colour alone
  • Error messages sit directly under the field they belong to and name the field
  • The success panel uses the same panel styling as the rest of the site
  • There is no artwork on this page beyond the shared header and footer: it is a task page, so the form is the content
TEXT:
  • h1: the registration title from the client dictionary
  • Group headings: your details, and booking
  • Labels: your name, email address, phone (optional), ticket type, number of tickets, and anything we should know (optional)
  • Submit label, and the cancel link label
  • Success heading and the receipt labels, including the total paid
  • The "no event chosen" heading and its instruction
AUDIO/VIDEO:
  • No audio and no video.
  • The submit button carries a busy state while the request is in flight, and the error summary is announced rather than only shown.
NOTES
  • Validation runs three times over the same rules: in the browser for an immediate, specific message, again in the API, and a third time in the database through the unique key and the CHECK constraints. The browser is a convenience, not the authority.
  • The ticket-tier options carry [selected] as well as the select's bound value. The options are created by a loop, so a value written before they exist is discarded and the browser shows the first option instead - which made the picker display one tier while the running total and the POST used another. Marking the option itself selected fixes the first paint.
  • A duplicate registration is refused with a 409 and is shown next to the email field using the project's own translated sentence, so a visitor reading the site in any of the four languages does not get the API's English message. The dictionary key exists in all four languages for exactly this case.
  • The confirmation is built from the API response, not from what the form thought it sent, so the receipt on screen is the row the database holds.
  • The running total is a computed signal over the form, so it cannot go stale: nothing has to remember to update it.
Description:

The write path. A form that validates in the browser and then creates a registration row through the API.

Content:
  • Event being registered for, and its ticket tiers <- GET /api/events/:id
  • Submit -> POST /api/events/:id/registrations
  • On success the response carries the new registration id and the computed total, which the receipt uses
  • A device-registration page is impossible by construction: there is no route for a bare /register, and the catch-all route shows the not-found page instead
Interactions:
  • Submit with empty required fields -> nothing is sent, each field is marked and the summary takes focus
  • Submit a valid form -> one POST, a busy button, then either the receipt or the API's field errors
  • Cancel -> back to the event page without writing anything
  • A duplicate email for the same event -> 409, shown beside the email field in the visitor's language
  • Change the tier or the quantity -> the running total updates immediately, with no request
Media Creation:
  • No artwork of its own: the page reuses the shared header, footer and card styling
  • All messages come from the dictionary, so the whole form translates, including the failure messages
Navigation:
  • Entry points: the Register control on an event page, which is the only way in
  • Leaves to: /events/:id on success or on cancel
  • The menu has no link to this page, because registration without a chosen event has no meaning
