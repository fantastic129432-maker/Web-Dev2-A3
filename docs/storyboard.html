Storyboard — 9 screens

PROG2002 A3 - Charity Events Website. One screen per page of the two websites. Every line below is taken from the delivered HTML, CSS and JavaScript, not written from memory.

HOME-01 — Home page

TITLE: Home page SCREEN ID: HOME-01 DATE: 30/09/2026

index.html

① ELEMENTS:
ELEMENTS:
  • Site header: brand, language picker, theme switch, menu (Home / Search Events / Admin site)
  • Hero copy block: eyebrow, h1, lead paragraph, two call-to-action buttons
  • "Next events at a glance" aside with an unordered list of the next three events
  • Statistics band with four stat tiles
  • Event grid: one card per current or upcoming event, plus a results count and a sort control
  • About section and Get in touch section
  • Site footer with the project note and the admin site link
GRAPHICS:
  • Hero uses a full-width dark brand panel with a soft radial wash (CSS gradient, no image file)
  • Each event card carries a 16:9 SVG illustration chosen from config.js EVENT_IMAGES
  • Four stat tiles in a responsive grid; the number is large, the label is small
  • Event grid is CSS Grid, auto-fitting columns, one column on narrow screens
  • Icons are inline SVG or text glyphs; no icon font is loaded
TEXT:
  • h1: "Every ticket you buy becomes help someone can feel."
  • Eyebrow: "Community charity events"
  • Buttons: "Browse upcoming events", "Search by date and location"
  • Section headings: "Where your support goes", "Current and upcoming charity events", "Who we are", "Get in touch"
  • Aside heading: "Next events at a glance"
  • Sort options: Date (soonest first) / Date (latest first) / Event name (A-Z) / Closest to goal
AUDIO/VIDEO:
  • No audio and no video element on this page.
  • The only moving part is the loading state: the panels show "Loading..." until the API answers.
NOTES
  • The hero and the two lower sections are static HTML; only the aside, the stats and the grid come from the API, so the page still reads sensibly if the API is down.
  • The heading level order is h1 then h2 for every section, which is what the accessibility check verifies.
Description:

Public landing page. Static welcome copy at the top, four live panels below it.

Content:
  • Next-events list <- GET /api/events/upcoming (limit 3)
  • Statistics tiles <- GET /api/stats (events, organisations, raised, goal)
  • Event cards <- GET /api/events/upcoming
  • Each card shows: illustration, state badge, category, name, short description, date, venue, price from, goal progress bar
Interactions:
  • Click a card or its "View details" link -> event.html?id=N
  • Change the sort control -> the grid re-renders in the browser, no page reload
  • Change language -> every labelled string switches, the choice is stored in localStorage
  • Change theme -> light / dark / follow system, applied before paint so there is no flash
  • Reset the filters link returns the grid to its default order
Media Creation:
  • Illustrations: hand-authored SVG committed to clientside/images/ (nine files, one per category)
  • No stock photography and no external image host, so nothing can 404 at marking time
  • Card layout is a reusable DOM helper in js/dom.js, so every card is identical by construction
Navigation:
  • Entry points: the site root, the brand link, or any menu item
  • Leaves to: search.html, event.html?id=N, admin/index.html, and the two in-page anchors #upcoming-events and #about
  • The menu deliberately has no "Register" item: registration is per event, so it starts from an event page

SEARCH-01 — Search events

TITLE: Search events SCREEN ID: SEARCH-01 DATE: 30/09/2026

search.html

① ELEMENTS:
ELEMENTS:
  • Breadcrumb: Home / Search events
  • Page header: h1 and a one-line lead
  • Filter panel with four fieldsets: When, Where, What kind of event, Other options
  • Date inputs (from / to) with a format hint under each
  • City input backed by a datalist of cities taken from the data
  • Category checkboxes, generated from the API
  • Two checkboxes: only free events, include past events
  • Apply and Reset buttons
  • Results region with a count line and the event grid
GRAPHICS:
  • Filter panel is a bordered card with a tinted header
  • The four fieldsets are numbered in their legends (1. When, 2. Where, 3. What kind, 4. Other)
  • Category checkboxes sit in a responsive auto-fit grid
  • Results use the same event card as the home page, so a card looks the same everywhere
TEXT:
  • h1: "Search charity events"
  • Filter heading: "Filter events" with the hint "All criteria are optional."
  • Legends: "1. When", "2. Where", "3. What kind of event", "4. Other options"
  • Labels: "From date", "To date", "City or town", "Only free events", "Include events that have already finished"
  • Hint: "Format: yyyy-mm-dd" and "Leave blank for any date. Example: 2026-10-01"
  • Results heading: "Matching events"
AUDIO/VIDEO:
  • No audio and no video.
  • The category list and the city suggestions are both fetched, so each shows a short loading line first.
NOTES
  • Every criterion is optional and they combine with AND on the server, not in the browser, so the same URL can be replayed and shared.
  • Filters are mirrored into the address bar; opening that URL again reproduces the same result set.
  • The filter form is novalidate: dates are checked in script so the message can be specific rather than a browser bubble.
Description:

Filter page. Four optional criteria, all applied as query parameters on one API call.

Content:
  • Category checkboxes <- GET /api/categories (name plus event count)
  • City suggestions <- GET /api/locations
  • Results <- GET /api/events with from, to, city, category, isFree, includePast, sort
  • Count line reads "N events found" and is announced through aria-live
Interactions:
  • Submit the form -> one API call, grid replaced, URL query string updated
  • Reset -> all criteria cleared, URL cleaned, full list returned
  • Check or uncheck a category -> applied on the next submit, not on every click
  • Click a result -> event.html?id=N
Media Creation:
  • No new artwork: the page reuses the event card renderer and the nine category SVGs
  • The numbering in the legends is text, not an image, so it translates with the rest of the page
Navigation:
  • Entry points: the menu, the home hero button "Search by date and location", or a shared filtered URL
  • Leaves to: event.html?id=N for any result, index.html via the breadcrumb
  • Returning to this page with filters still in the URL restores the same view

EVENT-01 — Event details

TITLE: Event details SCREEN ID: EVENT-01 DATE: 30/09/2026

event.html

① ELEMENTS:
ELEMENTS:
  • Breadcrumb: Home / Search events / Event details
  • Event hero: illustration, state badge, category, name, short description
  • Fact list: date and time, venue and city, capacity, organisation
  • Goal progress bar with the amount raised and the target
  • Full description and the "where the money goes" paragraph
  • Optional weather panel for the event date, when the venue has coordinates
  • Ticket tier table: tier name, price, availability
  • Registrations panel: how many have registered and how many tickets
  • Register button, or a disabled notice when the event is past
GRAPHICS:
  • Hero media is a 16:10 crop of the category SVG, object-fit cover
  • Goal progress is a CSS bar, filled proportionally, with the numbers beside it not inside it
  • Fact list is a two-column definition-style layout that stacks on narrow screens
  • State badge colour follows the event state: upcoming, ongoing or past
TEXT:
  • Section headings: "About this event", "Where the money goes", "Tickets", "Registrations so far"
  • Register button label: "Register for this event"
  • Past events show: "This event has already finished."
  • Weather panel states the forecast date and reads "Forecast for <date>"
AUDIO/VIDEO:
  • No audio and no video.
  • The page has one loading line that is replaced once GET /api/events/:id answers.
NOTES
  • The whole body is rendered by js/event.js into #event-root; the HTML file itself only carries the header, breadcrumb and footer, so there is one place where the layout is defined.
  • The Register control is a link to registration.html?id=N, not a button that posts here: the registration page owns the form and its validation.
  • Past events get a disabled control instead of a link, so the dead end is visible rather than silent.
  • The weather panel is optional and failure-tolerant: if the forecast request fails the panel simply is not shown, and the page is unaffected.
Description:

One event in full: the story, the numbers, the ticket tiers, and the way in to registration.

Content:
  • Event, tickets, progress <- GET /api/events/:id
  • Registration counts <- included in the same response
  • Weather <- GET api.open-meteo.com with the venue coordinates (external, optional)
Interactions:
  • Register -> registration.html?id=N
  • A past event shows a disabled button and explains why
  • Weather panel appears only when the venue has coordinates and the date is inside the forecast window
Media Creation:
  • Artwork is the category SVG, the same file the card used, shown at a larger crop
  • The progress bar is drawn with CSS from two numbers, so it cannot drift from the text beside it
Navigation:
  • Entry points: any event card on the home page or the search results
  • Leaves to: registration.html?id=N, back to search.html, or index.html through the breadcrumb
  • This is the only route into registration, by design

REGISTER-01 — Event registration

TITLE: Event registration SCREEN ID: REGISTER-01 DATE: 30/09/2026

registration.html

① ELEMENTS:
ELEMENTS:
  • Breadcrumb: Home / Search events / Event details / Register for an event
  • Event summary: the event being registered for, with its date and venue
  • Form: full name, email, optional phone, ticket tier, number of tickets, notes
  • Client-side error region above the form, filled with field-level messages
  • Submit button and a cancel link back to the event
  • Success panel after the row is created, with a link to the event
  • Neutral notice when the page is opened without an id in the URL
GRAPHICS:
  • Form is a single-column card, 640 px maximum, so the reading line stays short
  • Required fields are marked with an asterisk in the label, not with colour alone
  • Error messages sit directly under the field they belong to and name the field
  • Success panel uses the same panel style as the rest of the site
TEXT:
  • h1: "Register for an event"
  • Form heading: "Event registration"; lead: "Fill in the form below to reserve your place."
  • Labels: "Your name", "Email address", "Phone (optional)", "Ticket type", "Number of tickets", "Anything we should know? (optional)"
  • Submit: "Confirm registration"
  • Success heading: "Your place is booked"
  • Opened with no id: "Choose an event first" / "Registration is per event. Open an event from the home page or the search page and use its Register button."
AUDIO/VIDEO:
  • No audio and no video.
  • The submit button carries a busy state while the request is in flight.
NOTES
  • Validation runs twice: in the browser for a fast, specific message, and again in the API, because the browser cannot be trusted and the brief asks for validation on both sides.
  • The ticket dropdown is filled from the event, so the tier always belongs to the event being registered for.
  • The number of tickets is capped at the tier availability, and the API refuses anything above it with a field-level 400.
  • Opening the page with no id shows a neutral instruction rather than an error: the visitor has not done anything wrong.
Description:

The write path. A form that validates in the browser and then creates a registration row.

Content:
  • Event being registered for <- GET /api/events/:id
  • Ticket tiers <- same response
  • Submit -> POST /api/events/:id/registrations
  • On success the response carries the new registration id and the confirmation panel uses it
Interactions:
  • Submit with empty required fields -> the form is not sent, messages appear under each field
  • Submit a valid form -> one POST, button shows busy, then either the success panel or the API field errors
  • Cancel -> back to event.html?id=N without writing anything
  • A duplicate email for the same event is refused by the database unique key and surfaced as a clear message
Media Creation:
  • No artwork on this page beyond the shared header and footer: it is a task page, so the form is the content
  • All messages come from the dictionary, so the whole form translates
Navigation:
  • Entry points: the Register control on an event page, which is the only way in
  • Leaves to: event.html?id=N on success or on cancel
  • The menu has no link to this page, because registration without a chosen event has no meaning

admin/events.html

  • Count line, announced through aria-live

  • Long cells stack a primary line over a secondary line instead of wrapping awkwardly
  • Numeric columns are right-aligned; the table scrolls horizontally rather than squashing on narrow screens
  • The actions column holds text links, not icons, so nothing depends on an icon font
TEXT:

  • Lead: "Includes suspended and cancelled events, which the public website deliberately hides."

  • Row actions: "View", "Edit", "Delete"
AUDIO/VIDEO:
  • No audio and no video.
  • The count line and the feedback region are both live regions.
NOTES
  • This page reads the admin endpoint, not the public one; that is the whole reason a second endpoint exists.
  • Filters work the same way as the public search: optional, combined, and reflected in the URL.
  • The delete action is the visible half of the data-integrity rule. When an event has registrations the API answers 409 and the page explains why instead of failing silently.
Description:

The management table: every event, any status, with filters and a row action for each.

Content:
  • Rows <- GET /api/admin/events with status, state and keyword parameters
  • Registration and ticket counts come with each row, so the table needs one request
  • Delete -> DELETE /api/events/:id, which answers 409 when registrations exist
Interactions:
  • Apply -> refilter the table through the API
  • View -> opens the event on the public site in a new tab
  • Edit -> update.html?id=N
  • Delete -> confirmation first, then either the row disappears or the refusal is explained with the registration count
Media Creation:
  • No artwork; the table is the content
  • The status pill colours are defined once in CSS and reused by the dashboard tiles
Navigation:
  • Entry points: the admin menu, or the dashboard tile "Events"
  • Leaves to: update.html?id=N, the public event page, or the dashboard

TEXT:
  • h1: "Update a charity event"
  • Lead: "Choose an event, change what you need, and save. Only the fields you change are sent."

  • Nothing chosen: "No event chosen yet" / "Pick an event above to load its details and its registrations."
  • Tier hint: "Ticket types are listed for reference. The update endpoint adds tiers to an event that has none; edit the stored tiers in the database instead."

AUDIO/VIDEO:
  • No audio and no video.
  • Choosing an event triggers a second request, so the form and the registrations have their own loading states.

Description:

Pick an event, edit it, and see its registrations beside the form.

Content:
  • Picker list <- GET /api/admin/events
  • Chosen event <- GET /api/admin/events/:id, which includes its ticket tiers and registrations
  • Save -> PUT /api/events/:id with only the changed fields
  • Delete a row -> DELETE /api/registrations/:id
Interactions:
  • Choose an event -> form and registration panel load for it
  • Edit and save -> one PUT with the delta, then a confirmation naming the event
  • Save without changing anything -> the page says so rather than sending an empty payload
  • Delete a registration -> confirmation naming the attendee, then the row is removed and the count updates
Media Creation:
  • No new artwork
  • The form reuses the add page component, so the two pages cannot drift apart visually or in behaviour
Navigation:
  • Entry points: the admin menu, the dashboard card, or the Edit link on the events table
  • Leaves to: event.html?id=N or admin/events.html
  • Arriving with ?id=N preselects that event, so the events table can link straight into it
