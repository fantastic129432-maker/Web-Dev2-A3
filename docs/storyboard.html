Every line below is taken from the delivered components and their templates, the shared TypeScript library and the API, and re-checked against the running application on 17/10/2026 (API on :3000, public site on :4200, admin site on :4300), not written from memory.

HOME-01 — Home page

TITLE: Home page SCREEN ID: HOME-01 DATE: 17/10/2026

clientside/src/app/pages/home/home.ts + home.html · route /

① ELEMENTS:
ELEMENTS:
  • Application chrome, shared by both websites: layout/site-header.ts with the brand, the settings-bar (language picker and one theme button) and the menu (Home / Search events / Admin site), plus layout/site-footer.ts, which carries the contact details.
  • Hero: eyebrow, h1, lead paragraph and two call-to-action links - "Browse upcoming events" (in-page to #upcoming-events) and "Search by date and location" (router link to /search).
  • "Next events at a glance" aside (hero__panel) listing the first four rows of the same upcoming response, each a router link to /events/:id, with a link to the listing below.
  • Statistics band with four tiles: upcoming events, partner charities, raised through events, and the current funding goal. The goal tile carries one sentence naming what it counts.
  • Events section: a count line ("Showing 6 upcoming events.", a live region) and a grid of <app-event-card> components; there is deliberately no sort control here.
  • Loading, API-error and empty states for the aside, the statistics band and the listing; the statistics fall back to four "-- / Loading" placeholders, then to one explanation if the request fails.
  • About section with two sub-headings (how your donation is used, hosting your own event); the contact details are in the footer, which the About call to action links to.
GRAPHICS:
  • Hero is a full-width dark brand panel drawn with a CSS gradient; no image file is loaded for it.
  • Each event card carries a 16:9 illustration chosen from the nine committed SVGs, resolved from APP_CONFIG.imageBaseUrl plus the event's stored imageUrl, with fun-run.svg as the fallback.
  • The goal bar on each card is the shared progress-bar component, so the bar and the numbers beside it are computed from one value.
  • Statistics sit in a responsive grid; the number is large and the label small, and the goal tile adds a quiet scope note under the label.
  • The event grid is CSS Grid with auto-fit columns; one column on narrow screens.
  • Icons are inline SVG or text glyphs (the brand heart, the theme sun/moon); no icon font is loaded.
TEXT:
  • h1 and lead from the client dictionary, as every other string on the page is.
  • Section headings: Where your support goes, Current and upcoming charity events, Who we are, and the footer's contact heading.
  • Hero: the eyebrow "Community charity events", both call-to-action labels and the aside heading "Next events at a glance".
  • Count line "Showing {count} upcoming events." and the state badges on each card: Upcoming, On now or Past event.
  • No sort control on this page: sorting and filtering belong to the search page, which the hero links to.
AUDIO/VIDEO:
  • No audio and no video element on this page.
  • The moving parts are states rather than media: the aside, the statistics and the grid each show a loading line until the API answers; the language and theme switches repaint the page in place.
  • No media autoplays and nothing is embedded from a third party on this page.
NOTES
  • The page is one standalone Angular component in a zoneless application: the template's @if and @for blocks render from the component's signals, so there is no manual DOM update anywhere on the page.
  • Two requests feed it - GET /api/events/upcoming for both the aside and the grid, and GET /api/stats for the four figures - and both go through shared/src/api/api.service.ts. No component calls fetch and no component builds a URL. GET /api/organization is no longer called: the About mission is site copy in the dictionary, not API content, because the API's English mission used to win over the translated sentence and left a Chinese page with an English paragraph.
  • The list itself is not sorted in the browser. The API is asked for sort=date&direction=asc with a limit of 12, and the component renders whatever order the data is in; the hero panel is the first four rows of that same response, so the two can never disagree.
  • The language picker marks the selected <option> itself with [selected] as well as binding the select's value. A value written before a loop has created its options is discarded, and the browser then shows the first option - which is how a Chinese interface once displayed a picker reading "English". The register page's ticket-tier picker still uses the same fix; the search page's venue control is now a combobox whose text is a computed label, so the trap cannot recur there.
  • The header is the same height in all four languages - 65.31px from 900px up and 120.09px below, measured at 1440x1000 and 800x1000 - and the language picker and theme button sit at identical coordinates in every one of them; only the menu's translated labels change width, as they should. The interface-only note ("Interface language only; event details stay in English.") used to be a third child of the settings bar inside the header, which made the header 85.02px tall in the three languages that show it and forced the navigation to wrap; it now lives in a settings-note band below the header, still shown only when the language is not English.
  • The theme is applied before the application loads by a small inline script in index.html, so a dark-theme visitor does not get a white flash on every navigation.
Description:

Public landing page. Static welcome copy at the top, two live data sources below it, and one shared card component rendering every upcoming event.

Content:
  • Next-events aside <- GET /api/events/upcoming (limit 12; the first four rows are shown in the aside)
  • Statistics tiles <- GET /api/stats (6 upcoming events, 6 organisations, $99,290 raised, $197,000 active goal on the seeded data)
  • Event cards <- the same upcoming response, limit 12
  • Organisation block: not requested. The About copy comes from the dictionary and the contact details are static in the footer, so nothing in that section can be left in English by a failed request
  • Each card shows: illustration, state badge, category, name, short description, date, venue, price from, and goal progress
  • Only current and upcoming events appear here, because the upcoming endpoint is defined that way
Interactions:
  • Click a card or its "View details" link -> /events/:id
  • The event grid is not re-sortable here by design: the hero links to the search page for that
  • Change language -> every labelled string switches, the header keeps its height and control positions, and the choice is stored in localStorage under one key shared by both applications
  • Change theme -> light, dark or follow system, persisted and applied before paint
  • The page cannot hang: every API call carries a ten-second timeout and every failure becomes one ApiError, so there is a single error shape to render
Media Creation:
  • Illustrations: nine hand-authored SVG files, one per category, listed once in shared/src/config/app-config.ts so the public pages and the admin form cannot disagree about which artwork exists
  • No stock photography and no external image host, so nothing can 404 at marking time
  • Card markup exists once, in clientside/src/app/shared/event-card; the home page and the search page both render that component
Navigation:
  • Entry points: the site root, the brand link, or any menu item
  • Leaves to: /search, /events/:id, the admin site through the cross-site link, the footer's contact details, and the in-page sections
  • The menu deliberately has no "Register" item: registration is per event, so it starts from an event page

SEARCH-01 — Search events

TITLE: Search events SCREEN ID: SEARCH-01 DATE: 17/10/2026

clientside/src/app/pages/search/search.ts + search.html · route /search

① ELEMENTS:
ELEMENTS:
  • Breadcrumb: <nav aria-label="Breadcrumb"> with Home / Search events.
  • Page header: h1 and a one-line lead.
  • Filter panel with five numbered fieldsets: When, Where, What kind of event, Other options, and Event status.
  • Date inputs (from and to) with one format example under the fieldset; each date field has its own error message that is a live region.
  • Venue/town combobox: a text input with role="combobox", aria-autocomplete="list" and its own role="listbox". Typing filters the suggestions, the panel always opens downward, and suggestions are grouped under "Cities" and "Venues"; picking one commits the filter.
  • Category checkboxes, generated from the API, each with its active event count.
  • Other options: a "Only free events" checkbox and a keyword search field.
  • Event status radio group: Upcoming and current only / All events / Finished events only.
  • Action row: the sentence that the results update as the filters change, a "Search events" submit button and a "Clear filters" button.
  • Results region: a heading that carries the count ("Matching events (6)"), active-filter chips with remove controls, a six-order sort control, the "results shown in your chosen sort order" line when filters are set, and the event grid.
  • Three states: loading, API error, and done (either cards or the no-results panel). There is no idle state: the page searches as soon as it opens.
GRAPHICS:
  • Filter panel is a bordered card; each group is a fieldset with its own numbered legend (1. When, 2. Where, 3. What kind of event, 4. Other options, 5. Event status).
  • The combobox panel is an overlay anchored 4px below its input, with its own border and shadow and two visible group headings; the highlighted option and the committed option are distinct states.
  • Category checkboxes sit in a responsive auto-fit grid; the count is set quietly at the end of each label.
  • Results use the same event-card component as the home page, so a card looks the same everywhere.
  • Each active filter is a chip with a remove control, whose accessible name says which filter it removes.
  • Error messages sit directly under the field they belong to and take no space while empty.
TEXT:
  • h1: "Search charity events", with the lead explaining that any combination of date, location and category may be chosen.
  • Filter heading "Filter events" with the hint "All criteria are optional. Select one or many."
  • Five fieldset legends: 1. When, 2. Where, 3. What kind of event, 4. Other options, 5. Event status.
  • Labels: From date, To date, City or town, Keyword, Only free events, and the three status choices; the date hint "Leave blank for any date. Example: 2026-10-01".
  • Combobox text: the placeholder "Start typing, e.g. Lis", the hint "Suggestions come from the events in the database.", the group headings Cities and Venues, and "No matching city or venue."
  • Results heading and count, "Sort by", "Active filters:", the no-results heading and its widening hint, and the Search events / Clear filters labels.
AUDIO/VIDEO:
  • No audio and no video.
  • The results heading, the results grid, the count line in it and every field message are live regions, so a search that changes the results is announced rather than silently swapped.
  • The category list and the venue list are both fetched, so each shows a short loading line first; nothing autoplays and no media is embedded.
NOTES
  • Every criterion is optional and they combine on the server, not in the browser, so the same URL can be replayed and shared.
  • The Where field is a combobox rather than a native <select>, for two measured reasons. A native select's popup opens upward when the control is low in the viewport - it covered this field's label and the date filters above - and the browser owns that direction, so the page cannot fix it. The old placeholder also said "Start typing" on a control that could not be typed into. The box is now typeable, filters its own list, and the list is a panel anchored below the input, so it always opens downward.
  • Typing filters the suggestions only and sends no request: a half-typed word is not a filter the visitor has chosen. Picking a suggestion writes the same city:<name> or venue id the select wrote, into the same location query parameter, and applies the search at once, exactly as the select's change did. The groups are the seven distinct towns and eight venues from GET /api/locations.
  • The filters are written into the address bar and read back on load. The combobox's text is a computed label for the committed filter, so a deep link names its own filter on first paint; the old [selected] trap - a value written before a loop had created its options was discarded, and the page filtered by a venue while showing none - cannot recur here.
  • The whole filter form is one value held in a signal, so Clear is a single write and every control follows; there is no loop over the DOM. Typed controls wait 350ms after the last keystroke; checkboxes, radios and a combobox pick apply immediately. The two buttons are an explicit re-run and reset, not the step that makes a filter apply.
  • The component does not build a URL either. It produces the API's query parameters and hands them to ApiService, which owns the base URL, the timeout and the error shape. The search is one request, and the count in the results heading comes from the response's meta block, not from a second call.
Description:

Filter page. Five optional criteria, all applied as query parameters on one API call, with the state kept in the URL.

Content:
  • Category checkboxes <- GET /api/categories (name plus active event count)
  • Venue and town suggestions <- GET /api/locations (venues that host at least one active event; 8 venues and 7 towns on the seeded data)
  • Results <- GET /api/events with from, to, location, category, state, free-only and sort parameters
  • Count line <- the meta block of the same response
Interactions:
  • Change a control -> the results update: a checkbox, radio or combobox pick immediately; a date or the keyword after 350ms
  • Submit the form -> the applied query is re-run, the grid is refreshed and the URL is unchanged in meaning
  • Remove a chip -> that one criterion is cleared and the search runs again
  • Clear filters -> all criteria are cleared, the URL is cleaned and the full upcoming list is returned
  • Click a result -> /events/:id
  • Open a shared filtered URL -> the same view is restored, including the combobox's label
Media Creation:
  • No new artwork: the page reuses the event card component and the nine category SVGs
  • The numbering and legends are text, not images, so they translate with the rest of the page
Navigation:
  • Entry points: the menu, the home page's hero button, or a shared filtered URL
  • Leaves to: /events/:id for any result, and / through the breadcrumb
  • Returning to this page with filters still in the URL restores the same view

AUDIO/VIDEO:
  • No audio and no video.
  • The page has one loading line, replaced once the detail request answers, and the weather panel has its own later state because it is a second, external request. The weather section is aria-live="polite", so the forecast or its reason is announced when it replaces the loading line.

NOTES
  • The component reads the id from the route - /events/:id, not a query string - and loads the event with one request. That response also carries every ticket tier and every registration for the event, which is why the registrations table has no spinner of its own.
  • The registrations list is not sorted in the browser. The API returns them newest purchase first, with the registration id breaking ties, and the page renders them in the order they arrived, so exactly one place owns that rule.
  • The weather panel is on every event now. It used to be wrapped in @if (weatherPossible()), so with the seeded data exactly one event - the earliest, the only one inside Open-Meteo's 16-day window - carried a weather module, and the other nine event pages said nothing at all; a visitor cannot tell that from a broken page. The module is always rendered: a live forecast, or one sentence naming the four cases - the event has already finished, the venue has no map coordinates, the date cannot be read, or the date is beyond the daily forecast horizon - plus a loading line and a settled "No forecast is available for this venue and date." note. A bonus feature is still never allowed to break the page it decorates: the service resolves null rather than raising an error.
  • The public registrations table shows a masked attendee name ("Grace T.") and no email address or phone number. The API omits those two keys from the public response and sends attendeeDisplayName instead, and the page prints only that label; the full contact details remain available on the admin screens, which ask for them explicitly. This is data minimisation on a public page, not a display choice the template could quietly undo.
  • The progress figures come from the database view rather than from arithmetic in the browser, so the page and the admin dashboard cannot disagree.
  • One computed rule decides whether registration is open - the event is not past and not every published tier has sold out - and the hero's action, the status sentence and the tickets button all read it, so the three cannot contradict each other.
Description:

One event in full: the story, the numbers, the ticket tiers, the masked list of registrations, and the way in to registration. The weather module appears on every event and explains itself when no forecast is possible.

Content:

  • The public response omits attendee email and phone and adds attendeeDisplayName; the admin endpoint keeps the full row
  • Ticket availability and the sold count come from the same response as the event itself
  • On the seeded event 2 the two tiers are Single Seat ($185) and Table of Ten ($1,650); its page shows 3 registrations and 14 tickets sold, and a forecast is available for its 24 October 2026 date
Interactions:
  • Register -> /register/:id
  • A past or sold-out event shows a disabled button and explains why, rather than offering an action the API would refuse
  • The weather panel always says something: a forecast, a loading line, one of four reasons, or a no-forecast note; it never leaves a loading line behind
  • "Get tickets" scrolls to the tickets panel instead of navigating, so the reader does not lose their place
Media Creation:
  • Artwork is the category SVG, the same file the card used, shown at a larger 16:10 crop
  • The progress bar is drawn with CSS from two numbers, so it cannot drift from the text beside it
  • No map or stock photography: the venue is described in the fact tiles and the illustration is the category artwork
Navigation:
  • Entry points: any event card on the home page or the search results
  • Leaves to: /register/:id, /search, or / through the breadcrumb
  • This is the only route into registration, by design

REGISTER-01 — Event registration

TITLE: Event registration SCREEN ID: REGISTER-01 DATE: 17/10/2026

clientside/src/app/pages/register/register.ts + register.html · route /register/:id

① ELEMENTS:
ELEMENTS:
  • Page banner whose first line is the breadcrumb: Home / Search events / this event / Register for an event.
  • Banner content: eyebrow "Event registration", h1 and a lead line.
  • Two-column layout: an event summary card in a sticky rail on the left, and the form card on the right.
  • Summary card: event name, illustration, state badge, category, short description, date, time, venue, location, places left, and a "View details" link.
  • "Your details" group: full name, email address (with a hint that the confirmation is sent there), optional phone, and a notes field.
  • "Your tickets" group: ticket-type select and a stepper for the number of tickets (1-20, with disabled ends), followed by a running total.
  • Per-field error messages that are live regions, and one summary alert under the submit button after a failed submit.
  • Submit button with a busy label while the request is in flight; there is no cancel link in the form because the summary card already has the way back to the event.
  • Confirmation panel built from the API response: receipt rows and two actions (view the event, browse more).
  • Loading, no-event and problem states, each with its own heading and way out.
GRAPHICS:
  • The page is a two-column card layout: a brand-coloured event summary and a white form card, so the visitor can see what they are booking while typing.
  • Required fields are marked with an asterisk in the label, not with colour alone.
  • Error messages sit directly under the field they belong to and name the field.
  • The quantity stepper is two large buttons around a value, not a native number spinner.
  • There is no artwork on this page beyond the shared header, footer and the event's own illustration: it is a task page, so the form is the content.
TEXT:
  • Eyebrow "Event registration", h1 "Register for an event" and the lead asking for the form to be completed.
  • Group headings: Your details, Your tickets.
  • Labels: Full name, Email address, Phone number, Ticket type, Number of tickets, and Notes, with their hints and placeholders.
  • Running total line ("Total: 1 x $185.00 = $185"), submit label and busy label.
  • Success heading, its lead and email sentence, the receipt labels including the total paid, and the two actions.
  • The no-event heading and instruction, and the problem panel's heading and details.
AUDIO/VIDEO:
  • No audio and no video.
  • The submit button carries a busy state while the request is in flight, the error summary is announced with role="alert", and the running total is a live region.
NOTES
  • Validation runs three times over the same rules: in the browser for an immediate, specific message, again in the API, and a third time in the database through the unique key and the CHECK constraints. The browser is a convenience, not the authority.
  • The ticket-tier options carry [selected] as well as the select's bound value. The options are created by a loop, so a value written before they exist is discarded and the browser shows the first option - which once made the picker display one tier while the running total and the POST used another. Marking the option itself selected fixes the first paint.
  • A duplicate registration is refused with a 409 and is shown next to the email field using the project's own translated sentence, so a visitor reading the site in any of the four languages does not get the API's English message. The dictionary key exists in all four languages for exactly this case.
  • The confirmation is built from the API response, not from what the form thought it sent, so the receipt on screen is the row the database holds; the total and the tier in it come back from the same POST.
  • The running total is a computed signal over the form, so it cannot go stale; the quantity stepper clamps at 1 and 20 and disables the button at each end rather than letting the number run past them.
  • One @switch over the page state chooses between loading, no-event, problem, confirmation and the form, so impossible combinations cannot be expressed. There is no route for a bare /register; the catch-all route shows the not-found page instead.
Description:

The write path, with the event beside the form. A form that validates in the browser and then creates a registration row through the API.

Content:
  • Event being registered for, and its ticket tiers <- GET /api/events/:id
  • Submit -> POST /api/events/:id/registrations
  • On success the response carries the new registration id and the computed total, which the receipt uses
  • The places-left figure on the summary card comes from the same event response; the tier select shows each tier's remaining quantity
  • A device-registration page is impossible by construction: there is no route for a bare /register, and the catch-all route shows the not-found page instead
Interactions:
  • Submit with empty required fields -> nothing is sent, each field is marked and the summary is announced
  • Submit a valid form -> one POST, a busy button, then either the receipt or the API's field errors
  • Change the tier or the quantity -> the running total updates immediately, with no request
  • A duplicate email for the same event -> 409, shown beside the email field in the visitor's language
  • Use the summary card's View details link -> back to the event without writing anything
Media Creation:
  • No artwork of its own: the page reuses the shared header, footer, event illustration and card styling
  • All messages come from the dictionary, so the whole form translates, including the failure messages
Navigation:
  • Entry points: the Register control on an event page, which is the only way in
  • Leaves to: /events/:id on success or through the summary link, and /search from the receipt
  • The menu has no link to this page, because registration without a chosen event has no meaning
